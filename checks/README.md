# 「統制が効いている」検証項目（10 個）

まだ実機検証していません。初期状態は全件 Pending です。設定の存在と効果を分け、期待結果を確認できた場合だけ Pass、期待に反した場合は Fail、未実施・判断不能は Pending と記録します。

| C03 | 認証方式 | 統制試験 | 第8章（設定は第3・4章） | ローカル認証無効設定と Entra ID 呼び出しを確認し、認証なしの呼び出しを試す。キーは取得しない | 設定でローカル認証が無効、Entra ID は成功、未認証は拒否。これだけで実キーを使った拒否試験済みとはしない |

| C09 | ツール Gateway・ガードレール | ガードレール・統制試験 | 第4・8章 | ツール用 APIM の経由ログ・呼び出し quota と、Foundry の正常／拒否入力・RAI 適用を別々に確認 | quota の対象・集計キー・期間・上限・ポリシーは第7章で確定するまで Pending。本人経路・内部モデルのトークン quota を検証したとはしない。Preview は対象外 |

D14 により C02／C03 は App Service → Foundry の本人経路で確認します。C08 は人の入口の IP 制限、App Service → Foundry の VNet 規則、Agent Service → データ基盤、ツール用 APIM の許可主体・許可先を分けます。APIM の ID による拒否を IP 制限の成功と読み替えません。

C09 のツール quota は [quota-by-key](https://learn.microsoft.com/ja-jp/azure/api-management/quota-by-key-policy) 等の呼び出し回数・帯域の制限と、[LLM トークン制限](https://learn.microsoft.com/ja-jp/azure/api-management/llm-token-limit-policy)を区別します（取得日 2026-09-16）。一般の MCP 応答からモデルのトークン量を計測できるとは扱いません。

第8章では各 C 番号の中の試験行ごとに、許可条件の成功・条件を一つ変えた拒否・許可条件への復旧を記録します。GUI のボタン非表示は API 拒否、アプリのログイン要求は Foundry の未認証拒否の証明にはなりません。拒否した層を特定できない場合は Pending、期待する制御を通過した場合は Fail とし、未実施行のある C 番号を全体 Pass にしません。

C09 の quota はチャット回数ではなく対象ツール要求で確認し、最大要求数を事前に固定します。詳細な条件・記録項目・復旧手順は[第8章](../docs/08-governance-tests.md)を参照します。

## 証跡の書き方

各 ID に「実施日、対象Run、合成入力、期待結果、実結果、Pass / Fail / Pending、未解決点」を記録します。`evidence/` は公開対象外です。公開版には resource ID、ユーザー ID、社内ホスト名、本文、認証情報を含めません。C06 の後続試験など、未実施の部分を前半の完了に紛れ込ませません。

実施順は [README](../README.md)、試験操作は [第8章](../docs/08-governance-tests.md)、後片付けは [第10章](../docs/10-cleanup-cost.md) にあります。

第9章の C06 は正常構成の Audit、違反の Audit、許可構成の管理面更新、違反要求の Deny を分けて記録します。GUI で割当を保存しただけでは Pass にしません。現行の組み込み2定義は Foundry と AI Search が対象で、他のリソース型、承認モデル制限の適用、安全な違反要求の経路は保留です。認証や IP 制限を緩めて試験用の違反を作りません。

C07 はプラン確認、サンプルによる通知確認、AI 脅威の実検知、任意の CSPM 態勢確認を分けます。サンプルは模擬リソースのアラートであり、AI 脅威の実検知行を代替しません。設定だけで全体を Pass にせず、公式の安全な実検知試験が未確定なら Pending とします。詳細と根拠は[第9章](../docs/09-policy-defender-eval.md)を参照します。

C09の存在しないRAI IDによるfail open再現はhosted agent固有です。本編はRAIポリシーの存在・適用を確認し、実再現は付録Aの未実施分として分けます。C09全体を無条件Passにしません。評価・レッドチームは第9章の補足記録で、C番号は追加しません。


## C08 の判定を混同しない

| 項目 | 記録する内容 |
|---|---|
| 許可 IP | 対象リソース、権限、合成入力、成功結果 |
| 許可外 IP | 同等権限、拒否した層、ネットワーク規則との対応 |
| agent service | Cosmos / Storage / Search ごとの到達、信頼サービス例外 |
| App Service → Foundry | 統合サブネット、サービス エンドポイント、Foundry の VNet 規則とプロジェクト API の成否 |
| ツール用 APIM の認可 | 許可主体の成功と未認証・許可外主体の拒否。IP 制限とは別判定 |
| MCP | 未許可先の失敗と APIM 経由の許可先の成功。強制点が未確定なら Pending |
| 復旧時 | 変更前後の規則、対象、期間、復旧結果。公開範囲を緩めず、復旧できなければ停止 |

Entra のサインイン拒否だけではリソース側のネットワーク制限を確認したことにしません。APIM ですべて拒否された場合も、許可先の成功がないので合格ではありません。第7章のサービス発信経路が未解決なら Pending とします。

## C10 の削除と費用を混同しない

第10章では予算通知、RG 消失、稼働資産、論理削除、RG 外、Defender 復帰、削除後の費用を行ごとに記録します。アプリの削除だけで App Service プランの削除を済んだことにしません。保持待ち・費用反映待ち・権限不足は担当者と再確認日を添えて Pending にします。意図しない残存を確認した場合は Fail として修正します。

対象未作成は台帳を根拠に対象外とし、不明と区別します。全行を確認するまで C10 全体を Pass にしません。C10 の Pass は請求書の確定でも、C01〜C09 の未実施試験の合格でもありません。詳細と根拠は[第10章](../docs/10-cleanup-cost.md)を参照します。
