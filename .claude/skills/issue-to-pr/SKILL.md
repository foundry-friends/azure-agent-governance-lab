# Issue → Draft PR（1 件ずつ・確認しながら）

検証チームが立てた Issue を手順書に反映し、定例 MTG で全員が差分を確認できる Draft PR を作るための流れです。
PR のマージは、MTG で確認したあとに人が行います。develop にマージされた時点で本番の手順になり、Issue は `Closes #<番号>` によって自動で閉じます。

この Skill は、画面共有で複数人が見ている前で使われることがあります。応答は日本語・です／ます調で、短く書いてください。

## 守ること（理由つき）

- **GitHub に影響する操作は、1 つずつ確認してから実行する。** 対象は commit・push・PR 作成・PR の Draft／Ready の切り替え・Issue／PR へのコメントです。実行の直前に、内容（コミットメッセージ・コマンド・PR 本文）を見せて「〇〇を実行してよいですか？」と聞き、OK をもらってから実行します。前の OK を次の操作に使い回しません。共有リポジトリへの変更は取り消しにくく、MTG の前に意図しない変更が出ると、全員の確認が崩れるためです。
- **しないこと**：PR のマージ、Ready for review への変更（人が MTG のあとに行う）、main・develop への直接 push、強制 push、rebase、ブランチの削除、Issue の編集・クローズ。
  - AGENTS.md §8 は git 操作を禁止しています。ただし、それは Codex 向けのルールです。Claude Code では、この Skill の範囲（作業ブランチの作成・commit・push・Draft PR・コンフリクト解消のための develop の取り込み）に限って git 操作を行います。
- **1 Issue＝1 ブランチ＝1 Draft PR。** ブランチ名は `fix/issue-<番号>` で、必ず develop の最新から作ります。あとから履歴を Issue ごとにたどれるようにするためです。
- **作業する前に `pwd` とブランチ名を確かめる。** 別のフォルダやブランチで commit してしまう事故を防ぐためです。
- **実在の値をファイル・コミット・PR に書かない。** 対象は、ID・テナント・サブスクリプション・社内 IP・社内の URL（Microsoft Forms や共有ストレージを含む）・実名です（AGENTS.md §4）。Issue に URL が書かれていても転記しません。「検証チームから案内された〇〇」のように名前で書き、PR に「URL は Teams などで案内してください」と残します。Forms の URL の `id=` には、テナントの情報が入っています。
- **直すのは Issue が指す範囲だけ。** 同じ問題がほかの章にもあれば、自分では直さず、PR の「定例 MTG で確認したいこと」に「別の Issue で扱う」と書きます。

## 流れ

### 0. 対象を決める
- 依頼された Issue 番号を使います。番号の指定がなければ、`gh issue list --state open` で一覧を出し、番号の小さい順に提案します。
- `gh pr list --state open` も見て、すでに PR がある Issue は飛ばします。マージ済みの PR と重なる Draft PR があれば、先に「コンフリクトの解消」（下）を提案します。

### 1. Issue を読み直す
- 依頼の時点で、`gh issue view <番号> --json title,body,updatedAt,comments` で取り直します。依頼者が直前に Issue を書き換えていることがあるためです。
- 「章・工程」「実際に起きたこと」「直し方の案」を確かめます。
- 「直し方の案」が別の Issue とまったく同じなど、写し間違いに見えるところは、指摘して依頼者に確かめます。

### 2. 調べる（ファイルはまだ変えない）
- `git switch develop && git pull --ff-only` で、develop を最新にします。
- 次のことを調べます。読むのは develop の内容です。
  - 該当箇所の今の記述
  - 同じ言葉や記述が、ほかの章・README・`docs/ISSUE_RECORDING_GUIDE.md` にもあるか（`git grep`）
  - 変える見出しへのリンク元（`#アンカー` で `git grep`）
  - AGENTS.md のルールとぶつからないか。特に §2（状態行・出典）、§3（1 操作 1 文、「実行結果の確認ポイント」は 1 文、注記は 3 種類）、§4（実在の値）
  - 修正案の根拠になる、ほかの章の記述（例：その値を後の章のどこで使うか）
- Issue の「直し方の案」をそのまま使えない場合は、理由を添えて代わりの案を出します。例えば、URL がルールに反する、略称が規則と合わない、などの場合です。

### 3. 方針案を出して止まる
次の形で出して、依頼者の OK を待ちます。

```
## #<番号> の方針案（<Issue のタイトル>）

### 調べて分かったこと
- （該当箇所・ほかに出てくる場所・ルールとのぶつかり・根拠）

### 修正案（<ファイル>）
| 場所 | 今の記述 | 修正案 |
|---|---|---|

（変えないところと、その理由）

### 確認したいこと
- （依頼者が決めること。なければ書かない）

この方針で `fix/issue-<番号>` を作って修正してよいですか？
```

決めることが複数あり、選択肢がはっきりしている場合は、AskUserQuestion で聞いてもかまいません。

### 4. 修正して差分を見せる
- `git switch -c fix/issue-<番号>`（develop から作る）
- 方針どおりに直します。見出しを変えたら、リンク元のアンカーも同じブランチで直します。リンク先のファイルがあるかも確かめます。
- `git diff --stat` と `git diff` を見せ、変更点を表でまとめます。方針から外れた変更（リンクの修正など）があれば、そのことを書きます。
- 「LF will be replaced by CRLF」の警告は、改行コードについての通知です。差分が変えた行だけなら、問題ありません。

### 5. commit → push → Draft PR（それぞれ確認）
1. **commit**：メッセージを見せて確認 → `git add <変えたファイル>` → `git commit -F -`（ヒアドキュメント）
   ```
   docs(第N章): <何をどう変えたか>

   - <変更点>
   - <変更点>

   Refs #<番号>

   Co-Authored-By: <この環境で指定された共同作成者の行>
   ```
   commit では `Refs` を使います。Issue を閉じるのは、PR 本文の `Closes` の役目です。
2. **push**：`git push -u origin fix/issue-<番号>` を見せて確認 → 実行。push は、対象のリポジトリのフォルダの中で実行します（`git -C` は使わない。確認の設定が効かないため）。
3. **Draft PR**：タイトルと本文を見せて確認 → `gh pr create --draft --base develop --head fix/issue-<番号> --title "..." --body-file -`
   ```markdown
   ## 概要
   <何が分からなかったか（#番号）と、どう直すか>

   ## 変更内容
   | ファイル・場所 | 変更 |
   |---|---|

   ## 定例 MTG で確認したいこと
   - <Issue の案から変えた点と理由>
   - <範囲外にしたもの（別の Issue で扱う）>
   - <ほかの PR とのコンフリクトの見込み（同じ節を変えている PR 番号）>

   Closes #<番号>

   <この環境で指定された PR の署名行>
   ```
4. 作ったあと、`gh pr view <ブランチ> --json number,isDraft,baseRefName` と `gh issue view <番号> --json closedByPullRequestsReferences` で、Draft であることと Issue へのひも付けを確かめて報告します。

### 6. 次へ
PR の URL と Issue との対応を報告し、次の Issue の方針案に進みます。全件が終わったら、Issue・PR・状態の一覧表と、MTG でのおすすめのマージ順を出します。重なりの少ない PR を先にマージすると、コンフリクトの解消が少なくて済みます。

## コンフリクトの解消（マージ済み PR と重なったとき）
1. `gh pr view <番号> --json mergeable,mergeStateStatus` で、コンフリクトがあるかを確かめます。
2. 作業ブランチに切り替え、`git fetch origin` → `git merge origin/develop` を行い、衝突した箇所を見せます。rebase はしません（push 済みのブランチの履歴を書き換えると、強制 push が必要になるため）。
3. 解消の案（どちらの PR の意図をどう残すか）を出して止まり、OK をもらってから直します。
4. マージ commit と push は、それぞれ確認してから実行します。PR 本文の「定例 MTG で確認したいこと」に、解消した内容を追記してよいか聞きます。
