# B. 本番との差（Baseline）

本編の第0〜10章とは別の参考資料です。学習環境と本番設計の違いを確認するために使います。

> **Note** 状態: ドラフト（Learn 2026-09 時点の記述に基づく・未実行）。更新日 2026-09-17。本番の設計審査・構築・負荷試験・復旧試験は実施していません。

## B.1. 目的

本編で確かめられることと、本番移行時に追加で決めることを区別します。比較対象は閉域・WAF・APIM Standard v2・AI Search S1・Cosmos 3000 RU/s・Bastion・GRS を検討する本リポジトリの Baseline 案です。

### なぜこの作業が必要か

小規模な合成データで応答できることは、常時稼働・障害復旧・本番データの保護を満たすこととは異なります。費用を抑えた検証構成を、そのまま本番推奨と誤解しないために差分を残します。

Microsoft の Baseline 参照アーキテクチャを設計の根拠として使いながら、実際の業務要件に応じて構成を選びます。ここに挙げる SKU と台数が、どの組織にも共通する必須値という意味ではありません。

## B.2. 前提

本編は D14 の本人経路とツール経路を分けた構成です。Azure は未実行で、第4章の G1〜G3、第7章の本人認証・到達、第6章の C05 などは保留です。本編の実機確認と本番移行の判断を混同しません。

| 確認する前提 | 決める内容 |
|---|---|
| 対象業務 | 誰が何のデータを扱い、どの操作まで agent に許可するか |
| 信頼性 | 許容停止時間、許容データ損失、ピーク負荷、依存サービス停止時の扱い |
| データ | 保存・処理・複製の場所、保持期間、削除条件、復旧に必要なデータ |
| 管理 | ネットワーク、ID、データ、アプリ、監視ごとの所有者 |
| 予算 | 常時稼働、待機系、通信、ログ、復旧試験を含む見積り期間 |

> **Note** 要確認: この表の業務要件はまだ決まっていません。本番で採用する SKU・冗長性・リージョン・接続方式は要件と提供条件を照合して確定します。この付録は本番への変更承認ではありません。

## B.3. 構成の差を確認する

### 本編と本番で検討する構成

| 項目 | この検証 | 本番で検討する差 | 確認すること |
|---|---|---|---|
| Foundry への入口 | 社内 IP と D14 の統合サブネットを許可 | Private Endpoint とプライベート DNS | 利用者・アプリ・管理端末からの名前解決と経路 |
| Agent Service の送信 | G2 の通信方式が未解決 | BYO VNet と必要な閉域接続 | データ・モデル・ツールへの到達、必要な許可先 |
| Firewall | 自前の Firewall は構築しない | Azure Firewall Standard と送信制御 | 宛先別許可、例外、迂回経路、拒否の記録 |
| WAF | 構築しない | Application Gateway WAF 等の入口保護 | 公開要件、ルール、誤検知対応、監視担当 |
| APIM | Basic v2。ツール経路はネットワーク公開＋Entra の許可主体で制限 | Standard v2 等で本人経路も含めた経路を再設計 | 受信と送信の制限、本人委任、quota の対象 |
| AI Search | Basic、短時間の検証 | S1 を候補に負荷・容量・可用性を評価 | インデックス量、同時検索、レプリカ・パーティション |
| Cosmos DB | Serverless | Provisioned 3000 RU/s を本リポジトリの比較起点にする | agent のセットアップ条件、実負荷、調整方法、復旧 |
| 管理接続 | Bastion は構築しない | 必要な管理用 VM と Bastion の要否を判断 | 管理者の接続元、権限、操作監査 |
| Storage | Standard LRS | GRS 等を復旧要件で比較 | 複製先、データ損失の許容、切替方法 |
| ライフサイクル | 都度構築して第10章で削除 | 継続稼働、保護、変更管理、復旧手順 | 誤削除への保護と回復可能性 |

Microsoft の [Baseline 参照アーキテクチャ](https://learn.microsoft.com/ja-jp/azure/architecture/ai-ml/architecture/baseline-microsoft-foundry-chat) は、Private Endpoint や送信 Firewall、可用性・監視を含む構成です。本編の IP 制限や App Service のサービスエンドポイントを、これと同じ閉域構成とは呼びません。

Managed VNet は Preview の作成手順を対象外とします。本番案へ名前を追加するだけで採用済みにはしません。Agent 365 も本編・この付録の構築対象外です。

### APIM の受信と送信を分ける

Standard v2 の VNet 統合はバックエンドへ送信するための機能です。受信を非公開にする設計では、受信 Private Endpoint と公開アクセスの設定も別に確認します。SKU の変更だけで両方向の閉域化は完了しません。[APIM のネットワーク方式](https://learn.microsoft.com/ja-jp/azure/api-management/virtual-network-concepts)を参照します。

1. 利用者からアプリへの経路を記録します。
2. アプリから Foundry への本人経路を記録します。
3. Agent Service から APIM へのツール経路を記録します。
4. APIM から各バックエンドへの経路を記録します。
5. 各区間の認証主体とネットワークの許可条件を記録します。

本人経路を APIM に通す案では、本人の権限が下流へ正しく伝わることを改めて検証します。ツール要求の quota が動いたことを、モデルのトークン量や総費用の制限の証明にしません。

### データと復旧を分ける

AI Search の S1 は容量・性能を検討する候補です。レプリカとパーティションは別の判断で、S1 を選んだだけで必要な可用性を満たすとは扱いません。[サービスレベルの選択](https://learn.microsoft.com/ja-jp/azure/search/search-sku-tier)を参照します。

Storage の GRS は別リージョンへの複製を含みますが、geo レプリケーションは非同期です。復旧時点と失う可能性のあるデータを、アプリ・agent 状態・検索データも含めて評価します。複製を、必要な時点へ戻すバックアップの代用とは扱いません。[Storage の冗長性](https://learn.microsoft.com/ja-jp/azure/storage/common/storage-redundancy)を参照します。

Cosmos の3000 RU/sは本リポジトリの比較値です。すべての本番環境に十分な容量という意味ではありません。対象の [Standard setup](https://learn.microsoft.com/ja-jp/azure/foundry/agents/concepts/standard-agent-setup) の条件と、想定する会話数・保存量・実測した負荷を照合します。

## B.4. 本番へ進む前の確認

次の表は本番設計時の確認項目です。C01〜C10 の学習結果とは別の受入記録にします。

| 観点 | 確認する証拠 |
|---|---|
| 通信 | 期待する閉域経路の成功、公開・未許可経路の拒否、DNS の対応 |
| 認証 | 利用者とサービス主体の実効権限、無権限主体の拒否、緊急時の管理経路 |
| 容量 | 想定同時利用での応答時間、スロットリング、検索・保存の利用量 |
| 復旧 | バックアップからの復元、依存先の再接続、実測した復旧時間と欠損範囲 |
| 監査 | 必要な操作の追跡、本文の扱い、閲覧制御、保持・削除、通知先 |
| 変更 | 設定・アプリの版、適用前の確認、失敗時の戻し方、担当者 |
| 費用 | 常時稼働と冗長化、ログ・通信・モデル利用を含む見積りと実績比較 |

担当者が根拠を確認できた項目だけを完了にします。資料に機能が記載されていることと、組織の環境で受入済みであることを区別します。

## B.5. うまくいかない場合

| 問題 | 切り分けと対応 |
|---|---|
| 閉域化で接続できなくなった | DNS、経路、送信制御、ID を区間ごとに調べる。解消のためだけに全公開へ戻さない |
| SKU を変更しても性能が足りない | 検索、モデル、保存、アプリのどこで待っているかを測り、該当層の容量を見直す |
| 復旧したが会話を続けられない | agent の定義、状態、データ接続、ID とロールの再関連付けを確認する |
| 費用が見積りを超える | 稼働時間、冗長数、モデル利用、ログ量、通信量を分けて比較する |

原因・変更案・影響・戻し先を記録してから変更管理に従います。本番の保護設定や保持を、ラボの削除手順に合わせて外しません。

## B.6. 設計確認の完了と廃止

この付録の完了条件は、表の差分ごとに「採用／不採用／保留」、理由、所有者、確認する証拠が決まることです。実環境の構築完了や本番受入とは別です。

本番の廃止では、保持義務、復旧可能期間、下流の依存、権限、通信経路の順に影響を確認する計画を用意します。第10章の専用 RG 一括削除を、共有の本番資産へ適用しません。この付録自体では作成・削除を行いません。

No.1・5・9・10 も使用量・ライセンス・採用機能に応じて確認します。過去の約 $2,900/月は旧構成の概算で、現在の積算や予算承認の根拠にはしません。検証用の通常月 $57.56 も、常時稼働の本番へ換算した値ではありません。

> **Note** 要確認: 本番の数量・単価・契約条件が未確定のため、新しい合計額は算出していません。リージョン、SKU、台数、稼働時間、通信、保持、モデル利用量を決めた後、取得日付きの見積りを作ります。
