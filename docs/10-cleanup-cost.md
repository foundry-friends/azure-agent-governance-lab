# 10. 削除と費用を確認する

進め方: README の第0〜10章を順番に実施します。第9章までの結果を記録した後に進めます。途中で検証を中止する場合も、この章で作成済みの資産だけを片付けます。

> **Note** 状態: ドラフト（Learn 2026-09 時点の記述に基づく・未実行）。更新日 2026-09-20。Azure での削除・課金確認は未実施です。

## 10.1. 目的

必要な証跡を保存してから、検証資産を削除し、リソースグループ（RG）外の変更と費用を確認します。

### なぜこの作業が必要か

検証を終えても、App Service プランなどのリソースやサブスクリプションの有料設定が残ると、継続費用や他の利用者への影響が残ります。専用 RG の削除だけでは、論理削除された資産や Entra のアプリ登録まで片付いたことにはなりません。

削除の受付、RG の消失、論理削除の保持、費用への反映を分けて確認します。削除直後に判断できない項目は担当者と再確認日を決め、C10 を Pending として引き継ぎます。

## 10.2. 削除前の確認

1. 第1〜9章で保存したリソース名・ID・設定変更・試験結果の記録を開きます。
2. Azure portal の [ディレクトリとサブスクリプション] で記録と同じテナントとサブスクリプションであることを確認します。
3. portal 上部の検索欄で「リソース グループ」を検索します。
4. [リソース グループ] の一覧で専用 RG 名を検索します。
5. 対象の RG 名を選択します。
6. [概要] のサブスクリプションと RG 名を作成時の記録に照合します。
7. リソース一覧の名前・種類・場所を作成時の記録に照合します。
8. 次の削除台帳を非公開の `evidence/` に記録します。

| 項目 | 記録する値 |
|---|---|
| 対象 | テナント、サブスクリプション、専用 RG、Run、所有者 |
| RG 内 | Foundry account / project / deployments、Cosmos、Storage、Search、Key Vault、Log Analytics、Application Insights、APIM、App Service とプラン、Managed Identity、D14 の VNet とサブネット |
| RG 外 | 今回追加したロール割当・Policy・監視資産、アプリ登録と対応する Enterprise application、外部ツールの専用資産 |
| 変更前後 | Defender プラン、対象範囲、管理者との合意、今回の変更だけを戻す値 |
| 保持条件 | 証跡の保存先、保存期限、削除してよいデータ、Key Vault の保持日数と消去保護 |
| アプリの保存データ | 第7章のアプリ専用 Cosmos DB・コンテナー名、会話メモの保持要否。Agent Service 用とは区別する |
| 認証 | 第7章の専用アプリ登録の client ID と対応サービスプリンシパルの object ID、資格情報の保存場所。シークレット値は記録しない |
| 費用 | 検証開始日、削除開始・完了日時とタイムゾーン、最終確認日、再確認予定 |

専用 RG に他の利用者の資産が混在していれば、RG 全体は削除しません。所有者と削除範囲を確定してから進めます。既存ユーザー・グループ・共有サービスは対象外です。第1章で別 RG に置いた Cloud Shell のストレージは Run の終了ごとに削除しません。

RG を削除できても、削除済みリソースの照会・完全削除、サブスクリプションの費用参照、Defender 設定変更、Entra のアプリ削除ができるとは限りません。必要な管理者を台帳に記録します。作業用の権限は最後の確認まで残し、共有環境の権限を一括削除しません。

> **Note** 完全削除（purge）は復元できません。対象と保持条件の確認を終えた専用資産だけに適用します。実 ID を使った台帳・画面・ログは非公開に置き、公開手順へ転記しません。

## 10.3. 復帰と削除

下表の順に進めます。作成していない対象は、台帳を根拠に「対象外」と記録して次へ進みます。

| 順番 | 作業 | 次へ進む前に確認すること |
|---|---|---|
| 1 | 呼び出し終了・証跡保存 | 必要な結果を Azure の外に保存して開ける |
| 2 | VNet 統合の切断 | 専用アプリの統合先が解除されている |
| 3 | モデルのデプロイ削除 | 専用デプロイが一覧に残っていない |
| 4 | Defender の復帰・RG 外の割当整理 | 元からある共有設定と今回の変更を区別できる |
| 5 | Log Analytics の処理 | 完全削除か保持待ちかを記録している |
| 6 | 専用 RG の削除 | 削除通知と一覧の両方で結果を確認できる |
| 7 | 論理削除・Entra・RG 外の残存確認 | 保持期限と未処理の担当者が明確になっている |
| 8 | 費用確認 | 10.4 で反映待ちを含めて判定する |

### 呼び出しを終えて証跡を保存する

1. 利用者へ検証終了を伝えます。
2. アプリ・ツール・評価への新しい要求を止めます。
3. 実行中の処理が終了したことを確認します。
4. C01〜C09 の結果と未実施理由を `evidence/` に記録します。
5. 必要な合成入力のログ・評価結果・設定変更記録・費用画面を保存します。
6. 第7章の会話メモを保持する場合は、同章で確認したアプリ専用コンテナーの必要な合成データを、許可された非公開の保存先へ退避します。
7. 保存した証跡を開けることを確認します。

アプリ画面を閉じても、保存済み会話メモは消えません。アプリ専用 Cosmos DB が専用 RG 内にある場合は後の RG 削除対象に含めます。RG 外や共有アカウントに保存した場合はアカウント全体を消さず、専用 DB／コンテナーの処理を所有者へ引き継ぎます。第9章の評価用データ資産や結果も、親リソースを消す前に必要分を保存します。

第7章のアプリが未作成ならアプリの処理は対象外と記録します。ログの保存前に Log Analytics を削除しません。未完了の試験を Pass に変えてから片付ける必要はありません。

### D14 の VNet 統合を切断する

App Service を作成して VNet 統合した場合だけ実施します。統合を残したままアプリを先に消すと、サブネットに関連付けが残り、VNet の削除が妨げられる場合があります。

1. 専用 RG のリソース一覧から、台帳にある App Service の名前を選択します。
2. アプリの左メニューで [ネットワーク] を選択します。
3. [仮想ネットワーク統合] を選択します。
4. 表示された VNet 名・サブネット名を第7章の記録と照合します。
5. [切断] を選択します。
6. 確認画面が表示された場合は、対象アプリと切断先を確認して確定します。
7. 処理後に [ネットワーク] → [仮想ネットワーク統合] を開き直します。
8. 先ほどの統合先が解除されていることと、確認時刻を記録します。

切断に伴ってアプリは再起動します。以降はアプリの呼び出し試験を再開しません。サブネット自体はこの操作では消えないため、後の RG 削除と残存確認に含めます。接続を戻すために Foundry を全公開へ変更しません。

### 専用モデルのデプロイを削除する

1. 第4章で使用した Foundry ポータルを開きます。
2. 第4章の記録と同じ account／project を選択します。
3. 上部ナビゲーションの [ビルド] を選択します。
4. 左メニューの [モデル] を選択します。
5. 各デプロイの名前・モデル・デプロイの種類を台帳に記録します。
6. 今回の専用デプロイの名前を選択して詳細を開きます。
7. デプロイの削除操作を選択します。
8. 削除確認画面で対象名を照合して確定します。
9. [モデル] の一覧へ戻り、対象が消えたことを確認します。
10. 複数の専用デプロイがある場合は、1件ずつ同じ操作を行います。

> **Note** 要確認: 公式資料はデプロイ詳細から削除できることを示していますが、現行画面の削除ボタンと最終確認欄の表記は未確認です。検証時に表示名を記録し、対象デプロイを特定できない画面では確定しません。モデルカタログや共有デプロイを代わりに操作しません。

このラボの見積りは Global Standard です。実環境にプロビジョニング済みデプロイがあれば、account の論理削除中も課金が続く場合があるため、account より先に削除します。共有デプロイは削除せず、所有者の管理範囲として記録します。

### Defender と RG 外の変更を戻す

1. [Microsoft Defender for Cloud] を開きます。
2. [環境設定] から対象サブスクリプションを開きます。
3. [Defender プラン] の [AI サービス] と [Defender CSPM] を、第9章の変更前後の記録と照合します。
4. 今回変更したプランだけを、管理者と合意した復帰値へ変更します。
5. コンポーネントを変更した記録があれば、そのプランの [設定] で合意した値に戻します。
6. [Defender プラン] で [保存] が表示される場合は選択します。
7. [環境設定] から同じサブスクリプションを開き直します。
8. プランと対象コンポーネントの状態を台帳に記録します。

AI サービスの保存操作の表示差は第9章の保留事項を引き継ぎます。切替ボタンの操作だけでは復帰完了にせず、開き直した後の状態を確認します。

第9章で Defender for AI Services や任意の Defender CSPM を有効化した場合の復帰です。変更前から有効なプランはそのままにします。作業中に他チームの利用が始まった場合は、古い値へ機械的に戻さず管理者と復帰値を確定します。RG 削除をプランの無効化と扱いません。

1. 台帳にある RG 外の各スコープで [アクセス制御 (IAM)] を開きます。
2. [ロールの割り当て] で今回追加した主体・ロール・スコープを照合します。
3. 不要になった今回の割当の行だけにチェックを付けます。
4. [削除] を選択します。
5. 削除確認メッセージで対象を照合し、[はい] を選択します。
6. [ロールの割り当て] を再表示し、対象の割当が残っていないことを記録します。
7. 台帳にある RG 外の Policy があれば、[ポリシー] の [割り当て] を開きます。
8. 台帳のスコープに絞り、今回追加した割当の名前を選択します。
9. 定義・スコープ・割当名が一致することを確認します。
10. [割り当ての削除] を選択します。
11. 確認画面で削除を確定します。
12. 一覧を再表示し、対象の割当が残っていないことを記録します。

本編の予算と Policy は専用 RG スコープです。例外的な RG 外の変更がなければ「今回追加なし」と記録します。上位から継承する組織の Policy や既存のロールは削除しません。Managed Identity を消す前に RG 外の割当を照合しておくと、削除後の主体不明の割当を追いやすくなります。

### Log Analytics を処理する

保存済みの証跡だけで検証を終了でき、専用ワークスペースの復元が不要な場合は、RG より先に GUI で完全削除します。

1. [Log Analytics ワークスペース] から専用ワークスペースを開きます。
2. [削除] を選択します。
3. 表示された取り込み量と影響を確認します。
4. [ワークスペースを完全に削除する] を選択します。
5. 対象のワークスペース名を入力します。
6. [削除] を選択します。
7. [Log Analytics ワークスペース] の一覧へ戻ります。
8. 同じサブスクリプションで対象名を検索し、通常の一覧に残っていないことを確認します。
9. [ごみ箱を開く] を選択します。
10. 対象サブスクリプションの削除済み一覧に同名のワークスペースが残っていないか確認します。
11. 選択した削除方法・処理結果・確認時刻を台帳に記録します。

復元の余地を残す場合は手順4のチェックを付けずに削除し、[ごみ箱を開く] で対象が保持されていることを確認します。論理削除は14日間で、その後は復元できず、完全削除までさらに最大30日かかる場合があります。保持中は同名で新規作成できません。対象名・削除日時・再確認日を記録し、完全削除の確認行は Pending にします。

> **補足** 論理削除したワークスペースを途中で完全削除するには、まず回復してから削除し直します。元の RG がなければ RG の再作成も必要です。費用や他資産への影響を確認するまでは環境を復元せず、10.5 の対応として担当者へ引き継ぎます。

### 専用 RG を削除する

1. [リソース グループ] から対象の専用 RG を開きます。
2. 残っている資産を台帳と照合します。
3. [リソース グループの削除] を選択します。
4. 削除画面の対象一覧を確認します。
5. 確認欄へ専用 RG 名を入力します。
6. [削除] を選択します。
7. portal 上部のベルのアイコンから [通知] を開きます。
8. 対象 RG の削除通知を開き、成功・実行中・失敗のどれかを確認します。
9. [リソース グループ] の一覧へ戻ります。
10. 対象サブスクリプションを選択して一覧を更新します。
11. 専用 RG 名を検索し、対象が表示されないことを確認します。
12. 削除開始・完了の日時と通知結果を台帳に記録します。

削除の受付だけでは完了ではありません。失敗時は一部だけ消えている可能性があるため、10.5 で残存を確認します。ロックやバックアップの保護を無条件に外しません。

### 論理削除された資産を確認する

| 対象 | 確認する状態 | 名前の再利用・完全削除 |
|---|---|---|
| Key Vault | 実際の保持日数、消去保護、削除日時 | 保持は7〜90日。本編は7日を想定しますが実設定を優先します。消去保護が有効なら期限前の purge はできません |
| Foundry account | 対象 account の削除記録、デプロイの残存 | 保持は48時間。直ちに同名を使う場合は purge が必要です |
| API Management | 削除日時と予定 purge 日時 | 保持は48時間。保持中は同名を使えません |
| Log Analytics | 完全削除か、ごみ箱で保持中か | 前節の結果を照合します。RG 消失だけで完全削除と扱いません |

Key Vault は次の手順で確認します。

1. portal 上部の検索欄で「Key Vault」を検索し、個別リソースではなくサービスの [キー コンテナー] 一覧を開きます。
2. [削除されたコンテナーの管理] を選択します。
3. 対象サブスクリプションを選択します。
4. 台帳と一致する専用コンテナーのチェックボックスだけを選択します。
5. 削除前に記録した保持条件と消去保護を、表示された削除情報に照合します。
6. 完全削除する条件を満たす場合だけ [消去] を実行します。
7. 同じサブスクリプションの削除済み一覧を再表示して対象の状態を記録します。

消去には削除済みコンテナーに対するサブスクリプション側の権限も必要です。消去保護は管理者でも解除して回避できません。保持待ちは再確認日を記録します。

Foundry は次の手順で確認します。

1. portal の対象サービスの一覧で [削除されたリソースの管理] を開きます。
2. 対象サブスクリプションを選択します。
3. 台帳と対象 account を照合します。
4. 完全削除する条件を満たす場合だけ対象の [削除] を実行します。
5. 一覧を更新して対象の状態を記録します。

必要な `Microsoft.CognitiveServices/locations/resourceGroups/deletedAccounts/delete` はサブスクリプションのスコープで確認します。

> **Note** 要確認: Foundry account のサービス一覧における当該メニューの表示と、削除済み account の照合は Run 1 で確認します。Learn の一般的な Foundry Tools の手順を根拠としています。メニューがない場合は別のリソースを操作せず、管理者の確認待ちとします。

APIM の削除済み状態は、GUI を補う GA の Azure CLI で確認します。認証済み Cloud Shell の Bash で、次の値を置き換えます。

| 項目 | 値 |
|---|---|
| サブスクリプション | `'<subscription-id>'` を対象 ID に置換 |
| リージョン | `'<location>'` を作成時の場所名に置換（本編は `japaneast`） |
| APIM 名 | `'<apim-name>'` を台帳の専用名に置換 |

```bash
az apim deletedservice show --subscription '<subscription-id>' --location '<location>' --service-name '<apim-name>' --output json
```
実行結果の確認ポイント: 元のサービスとの対応、`deletionDate` と `scheduledPurgeDate` を記録し、権限不足や対象間違いを削除済みと判定しません。

結果に記載された `scheduledPurgeDate` と担当者を台帳に記録し、期限後に同じ対象を再確認します。日時末尾の `Z` は UTC です。記録した削除時刻と比較するときはタイムゾーンを揃えます。

| 照会結果 | 判定 |
|---|---|
| 対象の削除済みレコードが返る | 保持中。予定日時と再確認日を記録する |
| 対象が見つからない | 通常の APIM 一覧にも残っていないこと、指定したサブスクリプション・場所・名前が台帳と一致することを併せて確認する |
| 権限・認証・通信エラー | 照会未完了。完全削除と判断せず Pending にする |

### APIM を完全削除する (任意)

即時の完全削除が必要な場合だけ、台帳・保持条件・権限を確認して次の操作を選びます。APIM の purge にはサブスクリプションで `Microsoft.ApiManagement/locations/deletedservices/delete` と `Microsoft.ApiManagement/deletedservices/read` の権限も必要です。

```bash
az apim deletedservice purge --subscription '<subscription-id>' --location '<location>' --service-name '<apim-name>'
```
実行結果の確認ポイント: 完了後に上の照会で対象の残存を再確認し、コマンドの受付だけで C10 を Pass にしません。

### Entra と RG 外の専用資産を片付ける

1. 台帳で第7章用の専用アプリ登録の所有者と利用先を確認します。
2. Microsoft Entra 管理センターで対象テナントの [Entra ID] を開きます。
3. [アプリの登録] を開きます。
4. [すべてのアプリケーション] で第7章の専用アプリ登録名を検索します。
5. 対象の名前を選択します。
6. [概要] の [アプリケーション (クライアント) ID] を台帳と照合します。
7. [削除] を選択します。
8. 削除の影響を読み、確認のチェック欄がある場合は対象を確認してチェックします。
9. 確認画面の [削除] を選択します。
10. [アプリの登録] の通常の一覧へ戻り、対象が残っていないことを確認します。
11. [Entra ID] → [エンタープライズ アプリケーション] を開きます。
12. 台帳のアプリケーション ID に対応するサービスプリンシパルが通常の一覧に残っていないか確認します。
13. 台帳にあるその他の RG 外の専用資産の残存を確認します。

アプリ登録は RG の削除では消えません。ホームテナントでの登録削除に伴う対応サービスプリンシパルの削除を確認し、名前だけが似た別アプリは削除しません。Entra の削除済みアプリは通常30日間回復可能なため、保持状態も台帳に残します。既存の共用登録を利用していた場合は登録自体を削除しません。

第7章は Easy Auth で専用アプリ登録を作成し、資格情報を App Service の `MICROSOFT_PROVIDER_AUTHENTICATION_SECRET` に自動保存する手順です。資格情報の値を表示・コピーして廃止確認の証跡にしません。アプリ登録と App Service の削除結果をそれぞれ照合します。既存登録を使った場合や専用資格情報を別の場所にも保存した場合は、その管理者と廃止方法を確定してから処理します。未作成は理由付きの対象外、作成有無が不明なら Pending とします。

### スクリプトで RG を削除する (任意)

GUI の RG 削除だけを置き換える経路です。先に証跡保存・VNet 統合の切断・Defender 復帰・Log Analytics の処理を済ませます。GUI で削除を開始した後に重ねて実行しません。

1. Cloud Shell でこのリポジトリのルートを開きます。
2. 信頼できる `.env` のテナント・サブスクリプション・RG を照合します。
3. 次の `'<専用RG名>'` を `.env` と同じ専用 RG 名に置き換えて実行します。

```bash
bash scripts/teardown.sh --delete '<専用RG名>'
```
実行結果の確認ポイント: RG 消失の確認まで既定で最大約30分待ち、終了コード 2 の場合は削除待ちまたは未完了として扱います。

```bash
bash scripts/teardown.sh --status
```
実行結果の確認ポイント: 終了コード 0 は RG 不在、2 は RG が存在する状態であり、その他のエラーは原因を確認します。

削除は追加の対話確認なしで始まります。削除済み資産の purge、RG 外の片付け、Defender 復帰、費用の判定はこのスクリプトの対象外です。

## 10.4. 削除後の確認

### C10 の残存を記録する

[確認項目](../checks/README.md) の C10 を、次の行に分けて `evidence/` へ記録します。

| 確認行 | 期待結果・記録 |
|---|---|
| 第1章の予算 | 予算通知の設定証跡と、通知条件を満たした場合の受信結果がある。未発火と受信失敗を区別し、発火後の結果が不明なら Pending。ハードリミットとは扱わない |
| RG | 対象サブスクリプションで専用 RG が存在しない |
| 稼働資産 | [すべてのリソース] で台帳の資産が残っていない。特に App Service プラン・APIM・Search・専用 VNet を照合する |
| 論理削除 | 各サービスの確認を完了した。保持待ちなら期限・担当者・再確認日を記録する |
| RG 外 | 今回追加した権限・Policy・アプリ登録・監視・外部ツール資産を処理した。共有の継続利用は所有者と理由を記録する |
| Defender | 今回の変更を合意した状態へ戻した。残る有料設定の所有者が明確である |
| 費用 | 対象期間と反映状況を確認し、削除完了後の利用に由来する継続費用がないことを確認した |

稼働資産の確認は、Azure portal 上部の検索から [すべてのリソース] を開いて行います。対象サブスクリプションを選択し、RG の絞り込みを解除して、台帳の名前を1件ずつ検索します。見つかった行は種類・RG・リソース ID を照合し、同名の別資産を削除しません。親リソースの一覧に出ない DB／コンテナー等は、台帳の親リソースの削除結果と対応付けます。

アプリを停止・削除しても App Service プランが残れば費用が続きます。RG 外に作ったプランも照合します。対象未作成は台帳を根拠に対象外と記録し、照会できない状態と区別します。

### 費用の反映を確認する

1. portal で対象の [サブスクリプション] を開きます。
2. [コスト管理] の [コスト分析] を開きます。
3. スコープが対象サブスクリプションであることを確認します。
4. ビューの一覧が表示される場合は、カスタマイズ可能な [累積コスト] ビューを開きます。
5. 上部の日付選択で検証開始日から削除後を含む期間を指定します。
6. [細分性] を [日単位] に変更します。
7. [フィルターを追加する] を選択します。
8. 属性に [リソース グループ] を選択します。
9. 台帳の専用 RG を選択します。
10. [グループ化] をサービス名にして、サービス別の金額を確認します。
11. [グループ化] をリソースに切り替え、台帳の対象と内訳を照合します。
12. [ダウンロード] から表のデータを取得し、非公開の証跡へ保存します。
13. RG のフィルターを解除します。
14. 同じ期間のサブスクリプション全体の内訳で、今回の RG 外の資産と Defender の費用を照合します。
15. 確認日時・対象期間・スコープ・フィルター・通貨・金額・反映待ちの範囲を記録します。

日単位の表示期間は最大3か月（92日）です。長い検証期間は区切って確認します。[累積] の金額や予測値だけで削除後の利用を判定しません。ビューの表示差がある場合も、下表の確認条件が揃っていることを記録します。

| 項目 | 確認する条件 |
|---|---|
| スコープ | 台帳の対象サブスクリプション |
| 期間 | 検証開始〜削除後。削除当日だけで判断しない |
| 費用の種類 | 実際のコスト。予測や償却コストと区別する |
| 粒度・内訳 | 日単位、サービス別とリソース別 |
| 通貨 | 画面の通貨を記録する。円表示を Excel v3 の USD とそのまま比較しない |
| 再確認 | 初回の結果を残し、同じ条件で再確認した日時・差分を追記する |

削除済み RG がフィルター候補に出ない場合は、コスト詳細と保存したリソース ID で対応付けます。RG を作り直して確認しません。共有サブスクリプション全体の金額を自分の検証費用と扱いません。

コストデータの反映目安は EA / MCA で8〜24時間、従量課金で最大72時間です。翌日以降に契約種別に応じて再確認します。反映時間は保証ではなく、後から修正される場合もあります。削除当日の0円、データなし、閲覧権限なしを同じ結果にしません。過去の利用分の遅延計上と、削除完了後の利用分を分けて調べます。

### 補助スクリプトで案内を確認する (任意)

```bash
bash scripts/verify.sh --section 9
```
実行結果の確認ポイント: 旧セクション番号 9 は確認事項の案内のみで、終了コード 2 を返し、C10 の合格を判定しません。

```bash
bash scripts/cost_check.sh
```
実行結果の確認ポイント: コスト確認の案内を表示するだけで、実際の料金取得や請求確定は行いません。

## 10.5. うまくいかない場合

| 症状 | 切り分けと対応 |
|---|---|
| RG が消えない | [通知] と [アクティビティ ログ] の失敗対象を確認します。ロック・バックアップ・依存先を所有者と調べ、残存資産を再取得してから必要な対象だけ再処理します |
| VNet / サブネットの削除が失敗する | App Service の統合解除と service association link の残存を調べます。アプリが既に消えている場合は公式の VNet 統合トラブルシュートを管理者と確認し、対象サブネットを確定するまで一括削除しません |
| スクリプトが終了コード 2 | 削除要求の失敗か待機上限かを出力と portal で確認します。受付済みなら状態確認を続け、直ちに再削除しません |
| 消去が権限不足になる | 削除済み資産の操作に必要なサブスクリプション権限を管理者へ確認します。RG の権限だけで処理できると判断しません |
| Key Vault の消去保護が有効 | 保持期限と再確認日を記録します。保護を無効化する迂回手順はありません |
| Log Analytics を論理削除してしまった | 保持待ちか、回復して完全削除するかを保持条件に基づき決めます。回復が必要なら RG の有無と権限を確認し、再作成範囲を限定します |
| 削除済み一覧に対象がない | サブスクリプション・リージョン・名前・閲覧権限を確認します。権限エラーを完全削除の証拠にしません |
| 削除後も費用が増える | 利用日・計上遅延・残存プラン・デプロイ・Defender の範囲を照合します。反映待ちは Pending、意図しない残存が確認できれば Fail として修正します |

未解決の項目は、対象・実結果・次の操作・担当者・再確認日を残します。削除済み資産を原因調査のためだけに復元しません。操作前へ戻す必要がある場合も、回復可能な対象・データ保持・費用を確認してから個別に判断します。

## 10.6. 一周の完了条件

- 専用 RG と台帳上の稼働資産の消失を確認した。
- 論理削除された専用資産の処理と、RG 外の後片付けを確認した。
- Defender の今回の変更を合意した状態へ戻した。
- 削除後の利用に由来する継続費用がないことを、反映待ち期間を考慮して確認した。
- C01〜C10 の結果と未実施理由を非公開の証跡へ記録した。

保持・費用反映・管理者確認の待ちがあれば、削除操作が終わっていても C10 は Pending です。全確認行が期待結果を満たしてから Pass とします。C10 の Pass は請求書の確定や、他章の未実施試験の合格を意味しません。

再現確認は任意です。改めて第0章から新しい一周を始め、保持中の名前を使わないことを確認します。
