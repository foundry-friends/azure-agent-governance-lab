# 検証のIssue記録ガイド

> **Note** 検証チーム向けの記録用資料です。記載例はすべて架空で、Azureで発生・解決した事実や検証済みの結果ではありません。

## まず使うもの

[Excelサンプル（記載例付き）](../assets/templates/issue-register-sample.xlsx)を共有場所へ配置します。全員が共有Excelの課題台帳へ1件1行で記録します。最初はID・発見日・章と工程・種別・件名・実際に起きたことを埋めれば十分です。原因や修正案が分からなければ「未確認」と書きます。Excelの配布先・記入権限・証跡置き場・取りまとめ担当は検証チーム内で案内します。

| 記録 | 場所・ひな形 | 主な記入者 |
|---|---|---|
| 気づき・質問・手順との差・詰まり | 共有Excel（受付・Issueへ移さない課題の管理） | 全員 |
| 手順の修正が必要な差分 | [A：手順と違った](../.github/ISSUE_TEMPLATE/02-procedure-difference.md) | リーダー、または担当者 |
| 手順・計画の見直しが必要な詰まり | [B：詰まった](../.github/ISSUE_TEMPLATE/03-blocked.md) | リーダー、または担当者 |
| 日程・範囲・進め方の変更 | [C：計画の見直し](../.github/ISSUE_TEMPLATE/04-plan-change.md) | リーダー、または担当者 |
| 画面・条件・判定の根拠 | [非公開の証跡テンプレート](../checks/evidence_template.md) | 実施者 |

## 定例での流れ

1. リーダーが今回の章・工程・手順の版・到達目標と、共有Excelの置き場を案内します。
2. 全員が気づいた時点でExcelへ短く記録します。手順の不足・誤り・画面との差は、10分以内に解消しても残します。
3. 10分程度で詰まりが解消しなければ、その場の調査を切り上げて相談します。前提が揃わない後続工程は止め、独立した作業だけ進めます。
4. リーダーが記録を確認し、手順修正・計画見直しが必要な課題を1件1Issueへ転記します。重複は既存Issueへまとめ、Excelの課題IDと証跡番号を残します。
5. ExcelにはIssueリンクと状態「GitHubで管理」を記入します。転記後の進捗・議論・担当・解決判定はGitHubだけで更新し、Excelへの経過の転記は不要です。
6. 担当者がIssueの内容をClaude Codeへ渡して修正案を作り、人がレビューしてdevelop向けPRへ反映します。Issue作成だけで自動修正が始まる運用ではありません。
7. チームが修正版の対象工程を再確認し、結果をIssueに残してクローズします。計画だけの変更は、合意内容・反映先・次回の進め方を確認して閉じます。

修正不要で解消したものは、Excelに対応・確認結果を残して完了します。Issueへ移した行は、クローズ後も「GitHubで管理」とリンクを残し、最新状態はリンク先で確認します。ExcelとGitHubを両方更新する二重管理にはしません。

## 書く場所と公開範囲

GitHubが現在Privateでも、将来の公開を前提に記録します。

- **Issueへ書けるもの**：章・工程、手順のコミットSHA、実値を除いた操作、期待と実際の要約、エラーの種類、匿名の証跡番号、対応PR。
- **非公開へ置くもの**：必要な実リソースID、実IP、実施者の略号、マスクした画面、詳細な条件と実測結果。
- **どちらにも保存しないもの**：APIキー・トークン・パスワード・秘密鍵。rawログや画面はそのまま貼らず、必要な情報を抜き出して確認する。

入力・応答には合成データを使います。Issueに本文や社内ストレージのURLを貼りません。非公開ストレージが未決定なら、管理者が承認した保管先を決めてから証跡を共有します。

## 記載例1：共有Excelへの受付記録

**架空の例。** 共有Excelの1行に記入します。

```text
課題ID：EX-002
実施日／手順の版：<実施日>／<コミットSHA>
到達した章・工程：第7章 7.3 工程7のアプリ配布後確認
結果：詰まり
期待していたこと：送信するとエージェントの応答が表示される
実際に起きたこと：サインイン後に送信したが、エラーが表示された
試したこと／分かったこと：再読み込み後も同じ。原因は未確認
次に進めるか：依存するため停止
証跡番号：EV-001
関連Issue：未作成。リーダーへ切り出しを依頼
```

この段階で原因を断定する必要はありません。同じ症状の報告がすでにあれば、既存Issueに追加条件と証跡番号を追記します。

## 記載例2：A「手順と違った」

**架空の画面表示差の例。実際のAzure画面仕様を示すものではありません。**

| 項目 | 記載例 |
|---|---|
| タイトル | [手順差分] 第7章：設定項目を見つけるための補足が必要 |
| 発生箇所 | 第7章 7.3 工程3、docs/07-gateway-app.md、<コミットSHA> |
| 実施日・検証回・場所 | <実施日>、第1回、社内ブラウザ |
| 関連ログ・検証項目 | Excel課題ID EX-002、C08 |
| 手順の期待 | 指定された項目を選び、VNet統合の設定画面に進む |
| 実際 | 指定された項目名を見つけられず、画面内の別の場所から設定画面へ進んだ |
| 影響・範囲 | 今回は先へ進めた。同じ表示になる人数は未確認 |
| 試したこと | メニュー内を探して設定画面へ到達した。移動先の同一性は再確認が必要 |
| 修正案 | 画面差の可能性を確認し、必要なら「画面の見え方」に補足する |
| 証跡 | EV-002 |
| 原因の見立て | 表示変更の可能性があるが推測。言語・画面・権限の条件は未照合 |
| 対応 | 担当者が画面と公式資料を照合。再確認日<再確認日> |
| 修正PR・再確認 | 未作成／未実施。修正済みとして閉じない |

## 記載例3：B「詰まった」

**架空の例。403の原因や復旧方法を確定したものではありません。**

| 項目 | 記載例 |
|---|---|
| タイトル | [詰まり] 第7章：アプリから送信するとエラーになる |
| 発生箇所・版 | 第7章 7.3 工程7、docs/07-gateway-app.md、<コミットSHA> |
| 実施日・検証回・場所 | <実施日>、第1回、社内ブラウザ |
| 関連ログ・検証項目 | Excel課題ID EX-002、C08のApp Service → Foundry到達行 |
| 操作・期待 | サインイン後に合成入力を送信し、応答を得る |
| 実際 | 403を伴うエラー。拒否した層は未特定 |
| 切り分け | 再読み込み後も同じ。VNet規則と本人権限の照合は未実施 |
| 仮説 | 認可またはネットワークの条件が不足している可能性。未確定 |
| 影響 | 第8章の依存する試験へ進めない |
| 証跡 | EV-001 |
| 停止状態 | 設定変更なし。アプリ等の稼働資産が残っているため費用と次回までの保管を担当者が確認 |
| 次の対応 | 統合先・VNet規則・本人権限を照合。担当者と<再確認日>を設定 |
| 再実行・復旧 | 未実施／設定変更なし |

## 解決したときの追記例

**以下も架空です。修正内容に応じた実際の再確認で埋めます。**

```text
対応：手順の補足を修正PR <PR番号>で反映
確認した版：<修正後のコミットSHA>
再確認：<実施日>に対象工程を再実行し、期待結果と一致
証跡番号：EV-003
復旧：一時変更なし
後続への影響：依存する次の工程に進めることを確認
残る課題：当該Issueの範囲ではなし
判断：このIssueは解決。章全体の検証済み判定は別途実施
```

PRのマージでIssueが先に閉じられた場合も、実機の再確認が未実施なら「再確認待ち」を明記し、必要に応じて再オープンします。重複・対象外・取り下げは、解決と混同せず理由と引き継ぎ先を記録します。

## リーダーの整理と章の判定

担当者はGitHubのAssigneesで設定し、本文に実名を記入しません。状態は「未整理 → 調査中 → 修正／対応中 → 再確認待ち → 解決」を本文の対応欄で管理できます。ラベルは補助で、未作成でも記録を始められます。

ラベルを使う場合の候補は章別の `ch:03` 等と `手順差分`／`詰まり`／`質問`／`修正済み` です。`修正済み` は手順への反映を示し、実機合格を示しません。今回のテンプレートには存在未確認のラベルや担当者を自動設定していません。

章を「検証済み」にする条件は、事前に対象者を決めたうえで、**その章の完了条件を過半数が満たし、Excelに未整理・未対応の課題がなく、章の未対応Issueがゼロ**であることです。判定対象人数・完了人数・確認日・手順の版を記録します。欠席や未実施を成功扱いしません。未実施・失敗・対象外の試験行は[検証項目](../checks/README.md)のルールに沿って残し、過半数の成功で消しません。

## GitHubでの使い方

テンプレートが既定ブランチに反映された後、[Issues] → [New issue] からA・B・Cの用途を選びます。未反映の間は、各Markdownの先頭の `---` に囲まれた設定を除き、本文をコピーして使えます。例文の `<実施日>` や `<コミットSHA>` は実際の公開可能な値へ置き換えます。

これはテンプレートファイルの配置条件の説明です。GitHub上での選択画面・投稿は今回未確認で、実際のIssue作成やメンバーへの通知は行っていません。
