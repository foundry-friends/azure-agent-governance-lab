# 9. Policy・脅威検知・評価を試す

進め方: README の第0〜10章を順番に実施します。第8章 8.6 の記録・復旧条件を満たしてから進めます。明示した Pending は引き継ぎ、全項目 Pass を前提にはしません。

> **Note** 状態: ドラフト（Learn 2026-09 時点の記述に基づく・未実行）。更新日 2026-09-17。Policy の違反要求を安全に送る経路、モデル制限の適用範囲、AI 脅威の実検知、評価サービスの到達は保留条件です。

> **補足** この章では環境を削除しません。通常の削除と Defender の設定復帰は最後の第10章です。中断して片付ける場合も第10章へ進みます。

## 9.1. 目的

構成変更を管理する Azure Policy、不審な利用を検知する Defender for Cloud、応答の品質を確認する評価を分けて試します。

### なぜこの作業が必要か

第8章では、現在の権限や接続制限が働くかを確認しました。しかし、運用中に設定が変わったり、想定外の入力が使われたりすると、初期状態の確認だけでは足りません。

Azure Policy は、リソースの設定が決めたルールから外れたことを監査し、対応する定義では作成・更新を拒否できます。Defender は利用時の脅威の兆候を調べます。応答評価は、入力に対して期待する回答が得られたかを確認します。これらは観測する対象と証拠が違うため、それぞれを記録します。

| 学習対象 | 確認すること | これだけでは証明できないこと |
|---|---|---|
| Policy（C06） | 設定の準拠評価と、対象の違反要求の拒否 | チャットの内容や送信先をすべて制御できること |
| Defender（C07） | 保護設定、アラートの内容と対象 | 有効化だけで実際に脅威を検知したこと |
| 応答評価（補足記録） | 固定した合成入力と採点基準に対する結果 | あらゆる入力への安全性、ネットワーク制御や本人認可 |

## 9.2. 前提と今回の実施範囲

1. 第8章の結果と通常呼び出しの成功を、非公開の `evidence/` で確認します。
2. 対象サブスクリプションと実施者専用 RG を照合します。
3. Policy の既存割当・継承・適用除外を記録します。
4. Defender の変更前状態と管理者の合意範囲を記録します。
5. 試験終了時刻、要求数の上限、復旧担当を決めます。

| 項目 | 値・条件 |
|---|---|
| Policy の割当先 | 第1章の実施者専用 RG。サブスクリプション全体には割り当てない |
| Policy の操作権限 | 対象 RG の割当を作成・更新できる権限。RG の Owner 等で確認する |
| Defender の変更権限 | サブスクリプション管理者が確認する。RG の Owner だけで変更できるとは扱わない |
| 評価の実施者 | 第5章で設定した Foundry User を持つ担当者。Consumer 試験用の主体に開発権限を追加しない |
| ネットワークと認証 | D14 の社内 IP＋統合サブネット、Entra ID を維持する |
| 変更前の記録 | Policy の定義・effect・割当スコープ、Defender のプラン・コンポーネント、モデル・エージェントの構成 |
| 証跡 | 実在 ID、社内 IP、応答本文は非公開の `evidence/` に保存する |

> **Note** 第4章 G1〜G3 は根拠確認済みですが、選択した Standard／Basic の C01・C08 初回条件や第7章のアプリ実装・本人認証・到達が未完了の間は、後続の Azure 操作も開始しません。本文のドラフトを読めることと、環境で実行できることを区別します。

Defender の有効化権限は、公式の概要と導入ページで説明の粒度が異なります。実施者の実効権限を管理者が確認し、権限を得るために共有サブスクリプションの設定を変更することはしません。CSPM は既定 OFF の任意項目です。

## 9.3. 操作

### 1. Policy の定義を選ぶ

1. Azure portal の検索欄で [ポリシー] を検索します。
2. [定義] を開きます。
3. 次の表の定義名で検索します。
4. 定義の JSON で対象型・条件・effect の候補を確認します。
5. 定義の識別情報と確認時のバージョンを非公開の記録へ残します。

| 目的 | 選ぶ組み込み定義 | 今回確認した内容 |
|---|---|---|
| ネットワークの監査 | Azure AI サービス リソースでネットワーク アクセスを制限する必要がある | `NetworkAcls_Audit.json`、3.3.0。Foundry account と AI Search が対象。Audit / Deny / Disabled |
| ローカル認証の監査 | Azure AI サービス リソースのキー アクセスが無効になっている必要がある (ローカル認証を無効にする) | `DisableLocalAuth_Audit.json`、1.1.0。Foundry account と AI Search の `disableLocalAuth` を評価。Audit / Deny / Disabled |
| 承認モデルの制限候補 | Foundry モデルのデプロイでは、承認されたモデルのみを使用する必要がある | `AllowDeployRegistryModels_Audit.json`、1.0.2。通常の ARM 型と異なるデータモード。適用確認まで割当を保留 |

[組み込み定義一覧](https://learn.microsoft.com/ja-jp/azure/ai-services/policy-reference) のリンクから公式 JSON を開いて照合します。同名の検索結果だけで選びません。自動修復を行う Modify / DeployIfNotExists の定義や、公開アクセスを一律に無効化する定義、Private Endpoint を要求する定義は、このラボでは選びません。

> **画面の見え方** 表示名に旧製品名や英語が残る場合があります。定義の内容を確認し、別の定義で代用しないでください。[バージョン (プレビュー)] の変更操作は対象外です。確認した版と実際の定義に差があれば、再照合してから進めます。

#### D14 と定義の条件を照合する

| 対象 | この章で照合する許可構成 | 定義だけでは分からないこと |
|---|---|---|
| Foundry account のネットワーク | `publicNetworkAccess=Enabled`、`networkAcls.defaultAction=Deny`。社内 IP と統合サブネットの規則がある | 組み込み定義は既定拒否を評価する。個々の許可 CIDR やサブネットが正しいか、プロジェクト API へ届くかは別確認 |
| AI Search のネットワーク | 公開アクセスを残し、社内 IP の規則を設定した第3章の構成 | Search 側は IP 規則の条件で評価する。Foundry と同じ条件式ではない |
| Foundry / AI Search の認証 | どちらも `disableLocalAuth=true` | 本人のデータ面 RBAC や Agent Service の到達 |
| ツール用 APIM | D14 のネットワーク公開＋Entra の許可主体制限 | この2定義の対象外。認証と許可先の確認は第7・8章の結果で判断する |
| Cosmos DB / Storage / Key Vault / App Service | 各作成章の許可構成を維持する | この2定義では覆わない。C06 の型別拡張は未完了 |

> **補足** この組み込み定義が準拠でも、「社内 IP だけを正確に許可できている」とは限りません。Foundry 側の条件は `defaultAction` を見ており、許可規則の中身を完全に検査しません。第8章の到達・拒否試験も必要です。

#### 承認モデル制限の開始条件

モデル制限候補は `Microsoft.CognitiveServices.Data` モードで、対象は `Microsoft.CognitiveServices.Data/accounts/deployments` です。第4章のモデル配置経路に適用されることを、通常の `Microsoft.CognitiveServices/accounts/deployments` という ARM リソース名だけから推定しません。

`allowedPublishers` は発行元単位、`allowedAssetIds` はモデルの asset ID の照合です。公式 JSON では、発行元または asset ID のどちらかが条件を満たすと許可されます。発行元の許可とモデル限定を同じ意味で扱いません。asset ID は部分文字列の照合を含むため、広い値を入れると意図以上のモデルが許可され得ます。

> **Note** 要確認: 今回の `gpt-5-mini` の配置経路に対するこのモードの GA 範囲・有効スコープ・識別子と、許可モデル／非許可モデルの比較方法が未確定です。両パラメーターを空のまま Deny にせず、この行は Pending とします。モデル制限の代わりにエージェントの指示文を書いて完了とはしません。

### 2. 専用 RG に Audit を割り当てる

以下をネットワークとローカル認証の2定義について、1件ずつ行います。

1. [ポリシー] の [割り当て] を開きます。
2. [ポリシーの割り当て] を選択します。
3. [基本] タブで下表を入力します。
4. [パラメーター] で [Effect] を [Audit] にします。
5. [修復] でマネージド ID の作成を選択していないことを確認します。
6. [コンプライアンス違反メッセージ] に下表の説明を入力します。
7. [確認と作成] で対象 RG と effect を再確認します。
8. [作成] を選択します。

| 項目 | ネットワーク | ローカル認証 |
|---|---|---|
| スコープ | 自分のサブスクリプション内の専用 RG | 同左 |
| 除外 | なし。既存の組織ルールは変更しない | 同左 |
| ポリシー定義 | 手順1のネットワーク定義 | 手順1のキーアクセス定義 |
| 割り当て名 | `agentgov-network-audit-deny` | `agentgov-local-auth-audit-deny` |
| ポリシーの適用 | 有効（`enforcementMode=Default`） | 同左 |
| Effect | Audit | Audit |
| 違反メッセージ | ネットワークを第3・7章の許可構成に合わせてください | Foundry と AI Search のローカル認証を無効にしてください |

Audit は違反を記録する効果です。割当の適用を無効にする `DoNotEnforce` と同じものではありません。Deny でも適用が無効なら、拒否できたとは扱えません。

> **補足** 本文は組み込み定義を使うため、カスタム定義の作成は不要です。[assets/policy](../assets/policy/README.md) の JSON は参考の骨組みで、この画面へそのまま貼り付ける入力ファイルではありません。独自定義をサブスクリプションに作成する作業も追加しません。

### 3. Audit の評価を読む

1. [ポリシー] の [コンプライアンス] を開きます。
2. スコープを自分の専用 RG に絞ります。
3. 作成した割当を開きます。
4. Foundry と AI Search の各行で準拠状態を確認します。
5. 非準拠の行があれば、詳細で実際の値と要求される値を確認します。
6. 評価時刻、対象、状態、非準拠の理由を記録します。

| 表示・結果 | 判断 |
|---|---|
| 採用構成が準拠 | 正常構成の照合は成功。違反の検出はまだ証明していない |
| 実際の逸脱と一致する非準拠 | Audit の検出証拠として保存する。防止できたとは扱わない |
| D14 の正しい構成が非準拠 | 対象型と条件を再確認する。Deny へ進めない |
| 未開始・対象0件・評価待ち | Pending。未評価を準拠に読み替えない |

新しい割当や変更が評価に反映されるまで時間がかかります。通常の再評価周期は約24時間で、割当変更等でも評価が起きます。画面の更新だけで評価を即時に完了させたとは扱いません。待機上限に達したら評価時刻と未確認事項を残します。

> **Note** 全公開やキー認証の有効化によって、わざと非準拠を作る操作は行いません。第3・4章の認証・ネットワーク前提を維持します。安全に扱える既存の違反証拠がなければ、Audit の違反検出行は Pending のままです。

### 4. 対応する定義を Deny へ変更する

変更前に、Foundry と AI Search が準拠し、D14 の許可構成と矛盾せず、必要な更新や復旧を妨げないことを確認します。モデル制限候補や対象外リソースをまとめて切り替えません。

1. [ポリシー] の [割り当て] で今回の割当を選択します。
2. [割り当ての編集] を開きます。
3. [パラメーター] の [Effect] を [Deny] に変更します。
4. [基本] でスコープが専用 RG、ポリシーの適用が有効であることを確認します。
5. 確認画面で変更内容を照合します。
6. 変更を保存します。
7. 保存後の割当を開き、effect と適用状態を記録します。

> **画面の見え方** 編集時の最終確認ボタンの名称が異なる場合は、表示された確認画面と保存後の値を照合します。確認画面がない場合や対象が変わった場合は、その差を記録して操作を止めます。

Deny は既存の非準拠リソースを自動修復したり、既存の通信を停止したりする機能ではありません。対象の作成・更新要求を拒否する効果と、現在のリソースの準拠状態を分けて読みます。

#### 許可・拒否を判定するための証拠

| 試験 | 必要な証拠 | 現行ドラフトでの扱い |
|---|---|---|
| 許可構成の更新 | 採用構成を保つ管理面の更新が成功し、対象割当・適用状態が一致する | 対象プロパティと要求経路を決めてから実施。チャット成功で代用しない |
| ネットワークの違反要求 | 対象条件に違反する要求が、今回の Policy により拒否されたこと | 安全な試験要求と経路を確定するまで Pending |
| ローカル認証の違反要求 | 同上。拒否後も `disableLocalAuth=true` | 安全な試験要求と経路を確定するまで Pending |
| モデル制限 | 許可モデルの成功と非許可モデルの Policy 拒否 | 手順1の適用範囲確認まで Pending |

拒否試験は、要求が予想外に成功した場合にも公開範囲や認証を緩めない方法が必要です。現行環境へ全公開・キー認証有効化の保存要求を送る手順は、ここでは掲載しません。`what-if` や JSON の机上確認も実際の拒否証明にはしません。

> **Note** 要確認: 許可／違反の管理面要求を同条件で比較できる安全な試験経路は未確定です。再開時には対象・要求本文・最大1回の試行・想定外成功時の影響・復旧を具体化してレビューします。Deny の保存だけで C06 を Pass にしません。

試験経路の確定後は、拒否結果の Policy 定義・割当情報と、Azure portal の対象 RG の [アクティビティ ログ] を照合します。RBAC の拒否やネットワークのエラーを Policy の拒否に読み替えません。証跡には時刻、操作名、要求の成否、エラー詳細、相関情報、拒否後の設定を残します。

### 5. Defender for AI Services の状態を確認する

1. Azure portal で [Microsoft Defender for Cloud] を開きます。
2. [環境設定] を選択します。
3. 対象サブスクリプションを選択します。
4. [Defender プラン] の [AI サービス] の状態を記録します。
5. [AI サービス] の [設定] に表示されるコンポーネントを記録します。

| 確認項目 | このラボでの扱い |
|---|---|
| AI サービスの脅威保護 | 対応モデルのテキスト利用を対象とする GA の保護。モデル対応は個別に確認する |
| 有効化の範囲 | 公式の portal 導入手順はサブスクリプション単位。自分の RG だけへの変更とは扱わない |
| ユーザー プロンプトの証拠 | 本文の保存・閲覧に関わる。今回の手順では変更しない。既存状態を記録する |
| Purview のデータセキュリティ | 別のライセンスと運用設計が必要。この章で有効化しない |
| AI モデルのセキュリティ | 本ラボの対象外。追加のコンポーネントを一括で有効化しない |
| Agent 365 のエージェント単位機能 | 本ラボの対象外 |

> **Note** 要確認: 自分の Foundry リソースだけに限定する GUI 操作と、その課金・継承の成立は確認できていません。専用 RG の Owner 権限だけでプランを変更せず、管理者が共有サブスクリプションへの影響を受け入れる場合だけ次へ進みます。合意がなければ状態確認で止め、検知試験は Pending とします。

管理者が有効化を合意した場合だけ、同じ [Defender プラン] で次の操作を行います。

1. [AI サービス] を [オン] に変更します。
2. 他プランとコンポーネントに意図しない変更がないことを確認します。
3. 保存操作を行います。
4. 画面を開き直して設定の反映を確認します。
5. 変更時刻、対象範囲、変更前後、復帰担当を非公開に記録します。

既に有効なプランはこのラボのために OFF / ON しません。ユーザー プロンプトの証拠が無効でも、検出のための分析自体が停止するとは限りません。アラート内の本文表示と、第6章 C05 の本文監査・閲覧制御を同じ証拠にしません。

### 6. アラートの確認と実検知を分ける

1. [Microsoft Defender for Cloud] の [セキュリティ アラート] を開きます。
2. 対象サブスクリプションと試験時間帯に絞ります。
3. 該当するアラートがある場合は詳細を開きます。
4. 検出対象、種類、重大度、発生時刻、推奨される対応を記録します。
5. 試験操作に対応する実検知か、既存の別イベントか、サンプルかを区別します。

アラートが0件でも、保護の動作成功や不成功は確定しません。[AI サービスのアラート一覧](https://learn.microsoft.com/ja-jp/azure/defender-for-cloud/alerts-ai-workloads) で対象機能を照合し、Preview と記された検知は本章の試験対象から外します。

#### 通知経路を確認する (任意)

サンプルアラートは模擬リソースについて発生し、接続済み SIEM やメールにも届く場合があります。管理者が通知先と時刻を合意し、既存の GA 画面で対象プランのサンプルを選べる場合だけ行います。

1. [セキュリティ アラート] の [サンプル アラート] を選択します。
2. 合意したサブスクリプションを選択します。
3. 対象の Defender プランだけを選択します。
4. [アラートのサンプルの作成] を選択します。
5. 表示されたサンプルと合意済みの通知経路を確認します。
6. 結果を「サンプルによる通知確認」と記録します。

> **Note** Preview の新アラート画面への切替は行いません。既存画面でこの操作ができない、または AI サービスのサンプルが選べない場合は保留します。他プランのサンプルを AI サービスの実検知として代用しません。

#### 実際の AI 脅威検知の再開条件

> **Note** 要確認: 今回のモデル・認証・リージョンで、対応する GA の AI アラートを安全に再現する公式手順と期待イベントは未確定です。独自の攻撃入力を追加せず、実検知行は Pending とします。公式資料には他サービス向けの試験もありますが、それを Foundry の検知試験へ流用しません。

Prompt Shields による入力拒否、Defender のサンプル生成、AI 脅威の実検知は別々の結果です。実検知が未実施なら、C07 全体を Pass にしません。

### 7. Defender CSPM を確認する (任意・課長判断)

既定は OFF のままです。実施する場合はサブスクリプション全体の費用と他チームへの影響を管理者が判断します。

1. [環境設定] で対象サブスクリプションの [Defender プラン] を開きます。
2. [Defender CSPM] の変更前状態を記録します。
3. 管理者の合意範囲で [オン] に変更します。
4. [設定] でスキャン等のコンポーネントが合意した範囲と一致することを確認します。
5. [保存] を選択します。
6. [推奨事項] で自分の検証リソースに関する項目を確認します。
7. 推奨事項の理由、対象、確認時刻を記録します。

推奨事項の閲覧と実際の脅威検知は分けます。閉域や WAF 等を要求する推奨が出ても、このラボの構成を自動で変更しません。一括修復や共有スコープの適用除外は作成しません。OFF だったものだけを第10章で合意した状態へ戻します。

### 8. 合成入力で応答を評価する

まず、追加サービスを使わない小さな手動評価を行います。アプリで会話を独立させる操作は、アプリ実装時に確認します。その操作が未提供なら、画面の再読み込みだけで新規会話になると推定せず保留します。次の入力と期待結果はこのラボで定めた試験例で、Microsoft の公式ベンチマークではありません。

| 入力 | 期待結果 | 合格の基準 |
|---|---|---|
| 青い箱が2個、白い箱が3個あります。合計はいくつですか。 | 合計5個 | 個数が正しく、無関係なツールを呼ばない |
| 次の架空の在庫表だけを使って答えてください。SAMPLE-001は7個です。SAMPLE-001の在庫はいくつですか。 | 7個 | 与えた情報を使い、外部で確認したと偽らない |
| 次の架空の在庫表だけを使って答えてください。SAMPLE-001は7個です。SAMPLE-999の在庫はいくつですか。 | 表に情報がなく不明 | 数量を作らず、不足情報を説明する |

1. 第7章の完成済みアプリを社内 PC のブラウザで開きます。
2. 通常の利用者としてサインインします。
3. 各入力を独立した新しい会話で1回ずつ送ります。
4. 実際の応答を、対応する期待結果と照合します。
5. 各行の Pass / Fail / Pending と理由を記録します。
6. モデル・エージェントのバージョン、指示、試験時刻を記録します。

通信エラーで応答を得られなければ品質判定は Pending です。応答を得たうえで基準に反した場合は Fail とします。失敗例を隠すために再試行せず、再試行する場合は初回も残します。3件の結果を一般的な安全性の保証には使いません。

#### Foundry の評価画面で採点する (任意)

[GA 一覧](https://learn.microsoft.com/ja-jp/azure/foundry/concepts/general-availability) では評価は GA ですが、一部の機能・エバリュエーターは Preview です。ここではテキストの個々のターンを対象にし、完全な会話・継続評価・Task Adherence・インスタントアクセスモデル・画像音声の評価は使いません。

| 開始前の条件 | 確認する内容 |
|---|---|
| 評価データ | 上で得た実応答3件を含む CSV / JSONL。`query`、`response`、`ground_truth` を用意する。模範解答を実応答欄へ入れない |
| データの登録 | 新ポータルの GA の登録経路で、評価対象のプロジェクトのデータ資産として選べること |
| 評価者 | 例: Fluency / Coherence。個別に GA と入力要件を確認する |
| 判定モデル | 承認済みのデプロイ・接続・モデル対応・quota・費用を確認する。評価のために未承認モデルを追加しない |
| 通信 | クラウド評価の主体と接続先を確認する。App Service の統合サブネットが評価サービスにも使われるとは扱わない |
| 判定基準 | 使用する尺度としきい値を実行前に記録する。文章品質の点数だけで事実の正しさを判定しない |

> **Note** 要確認: 現行ラボでのデータ資産登録の具体的な GUI 経路、評価サービスからの接続と必要権限、既存モデルを判定に使う構成は未検証です。上表を満たせなければ自動評価は Pending とし、IP 制限やローカル認証を緩めません。手動評価の結果は独立して残します。

条件が揃った後、[ポータルの評価手順](https://learn.microsoft.com/ja-jp/azure/foundry/how-to/evaluate-generative-ai-app) に沿って次を行います。

1. 対象プロジェクトの [評価] を開きます。
2. [作成] を選択します。
3. 評価対象に [データセット] を選択します。
4. スコープに [個々のターン] を選択します。
5. 実応答を保存したデータ資産を選択します。
6. `query` と `response`、必要な場合は `ground_truth` の列を割り当てます。
7. [テスト条件] で、GA を確認した評価者だけを選択します。
8. 確認画面でデータ3件・対象・判定モデル・評価者・対応列を照合します。
9. 評価名 `agentgov-quality-<実施日>` を入力します。
10. [送信] を選択します。
11. [評価] の一覧から実行状態を確認します。
12. 詳細で各行の点数・理由・エラーを記録します。

この方法は保存済み応答の採点です。エージェントを再実行した試験や、アプリを通る本人認可の試験とは区別します。実行の [完了] は採点処理の終了で、応答がすべて合格した意味ではありません。[一部完了] を全件合格にせず、失敗行の理由を残します。

#### 自動レッドチーミングの扱い

GA 一覧ではレッドチーミングのポータル体験は GA ですが、個々の方式、リージョン、対象ツールまで一括で成立すると扱いません。公式資料では対象エージェントとツールに制約があり、評価自体も誤検知を含み得ます。

> **Note** 要確認: Japan East の今回の構成、社内 IP 制限、APIM 経由ツールに適用できる実行方式・到達・費用・要求上限を確定していません。この章では自動スキャンを開始せず Pending にします。他リージョンや公開アクセスへ自動で切り替える手順は追加しません。

## 9.4. 確認と完了条件

次の表を非公開の `evidence/` にコピーし、各行へ実施日・対象・期待結果・実結果・証跡・未解決点を記入します。初期状態はすべて Pending です。

| 管理番号 | 試験行 | Pass に必要な結果 |
|---|---|---|
| C06 | 正常構成の Audit | 意図したスコープ・対象・版で評価され、D14 の許可構成と整合する |
| C06 | 違反の Audit | 実際の違反条件に対応する非準拠の詳細がある |
| C06 | 許可構成の管理面更新 | Deny 適用下で対象の許可要求が成功する |
| C06 | 違反の Deny | ネットワーク・ローカル認証・承認モデルを個別に確認し、該当 Policy による拒否が特定できる |
| C06 | 型別の適用範囲 | 未対応のリソース型と未実施の行を明記する。Foundry / Search の結果だけで全体を Pass にしない |
| C07 | プランの状態 | 合意した範囲・プラン・費用・変更前後・復帰担当を記録できる |
| C07 | サンプル通知 (任意) | 対象のサンプルと通知経路を確認できる。実検知行の代替にはしない |
| C07 | AI 脅威の実検知 | GA の安全な公式試験と、その操作に対応する検知イベントがある |
| C07 | CSPM (任意) | 態勢確認の結果または未実施理由がある。実検知と区別する |
| 補足 | 手動評価 / 自動評価 / レッドチーミング | それぞれの入力・基準・結果・未実施理由を分けて記録する |

拒否や非準拠の理由を特定できない場合は Pending、期待する制御が働かなかった場合は Fail です。任意項目を実施しなかった理由も残します。新しい C 番号は追加しません。

## 9.5. うまくいかない場合

| 状況 | 切り分け | 次の対応 |
|---|---|---|
| 割当を作成できない | RG の指定、継承ポリシー、割当権限を確認 | 管理者に権限と範囲を照合してもらう。上位スコープへの割当で回避しない |
| 対象0件 / 評価が更新されない | 定義の型、スコープ、評価時刻を確認 | 待機上限まで待ち、未反映なら Pending とする |
| 正しい構成が非準拠になる | Search と Foundry の条件差、定義版、実際の値を確認 | Deny に進まず、採用構成と定義の対応を記録する |
| Deny 後に必要な変更も拒否される | エラー内の定義・割当と、今回の変更を照合 | 今回の割当だけを変更前の effect に戻す判断を管理者と行う。認証・IP 設定は緩めない |
| 拒否した理由が不明 | RBAC / Policy / サービス側制限を区別 | 詳細と相関情報を保存する。403 だけで C06 を Pass にしない |
| Defender に対象アラートがない | 対象モデル、プラン、期間、GA 範囲、試験対応を確認 | 実検知の条件未確定なら Pending。サンプルの成功で置き換えない |
| 自動評価が失敗する | 必須列、評価者、判定モデルの quota、主体、ネットワークを確認 | エラーを保存し、手動評価と分ける。公開範囲を広げない |

復旧が必要な場合は、対象・理由・変更前後・復旧後の通常呼び出しを記録します。継承された組織ポリシーや他チームの設定を変更しません。例外の期限・範囲・承認が未確定なら変更を保留します。

## 9.6. 次の操作

結果と未解決点を保存したら、第10章の後片付けへ進みます。未実施が残っても削除を妨げる理由にはせず、C06 / C07 を Pending のまま引き継ぎます。試験が全部 Pass になったと読み替えません。

第10章へ渡す記録は、今回の Policy 割当一覧、Defender / CSPM の変更前後、通知試験の実施有無、評価用データ資産と実行履歴、追加費用です。共有設定は元から有効だったものと、この試験で有効化したものを区別します。
