# 9. Policy・脅威検知・評価を試す

進め方: README の第0〜10章を順番に実施します。第8章の完了条件を満たしてから進めます。

> **Note** 状態: 構成ドラフト・操作の詳細は未確定（Azure 未実行）。構成変更日 2026-09-15。

> **補足** この章では環境を削除しません。通常の削除は最後の第10章です。中断して片付ける場合だけ、第10章へ進みます。

## 9.1. 目的

統制層⑤・⑥・⑨として、Policy の監査と拒否、Defender、合成入力による評価を分けて確認します。

### なぜこの作業が必要か

第8章で現在の権限や接続を確認した後は、運用中の設定変更や不審な利用、応答の品質にも目を向けます。初期状態が正しくても、後から設定が変わることや、想定外の入力が使われることを考慮するためです。

この章では、構成ルールからの逸脱を扱う Policy、脅威の兆候を扱う Defender、合成入力に対する応答の評価を別々に試します。まず監査で影響を把握してから拒否設定を検討し、検知や評価もそれぞれの証拠で判断します。一つの試験に合格しただけで、残りも確認済みとはしません。

## 9.2. 前提

通常の呼び出しと統制試験を記録済みです。Policy 割当は自分の RG に限定します。Defender の変更は共有サブスクリプションへの影響と復帰方法を管理者と合意します。

## 9.3. Audit → Deny → 検知・評価の順に試す

### Policy を割り当てる

1. [Policy] の [定義] で対象リソース型と許容 effect を確認します。
2. [パラメータ例](../assets/policy/assignment.example.json) をローカル設定へコピーします。
3. 最初は `effect=Audit` に設定します。
4. 対象を専用 RG に限定して [割り当て] を作成します。
5. [コンプライアンス] で非準拠と理由を確認します。
6. 同じ章で下表の拒否対象を個別にレビューします。
7. 定義が対応する場合だけ `effect=Deny` に変更します。

| 項目 | 値 |
|---|---|
| 無制限公開の拒否 | 公開が Enabled かつ既定 Allow／IP 規則なし等を型別に評価（公開 Enabled 自体は禁止しません） |
| ローカル認証の拒否 | Foundry / Cosmos / Search の `disableLocalAuth`、Storage の `allowSharedKeyAccess` を型別に評価 |
| モデル制限 | 承認モデル限定 |
| 最初の試験 | Audit、違反を記録 |
| 次の試験 | Deny、許可構成の成功と違反構成の拒否を確認 |

> **Note** 要確認: [定義例](../assets/policy/unrestricted-network.example.json) と [認証例](../assets/policy/local-auth.example.json) は Foundry のみの骨組みです。alias・型別の条件・空配列の意味・対応 effect を確認し、他の 6 リソースに対応したとは扱いません。Audit と `DoNotEnforce` は同義ではありません。41 の初期設定や データ接続の復旧と Deny が競合する点も未解決です。

### Defender for AI Services を確認する

1. [Defender for Cloud] の [環境設定] で対象サブスクリプションを選択します。
2. [Defender プラン] で変更前状態を記録します。
3. 合意した AI Services のプランだけを設定します。
4. [セキュリティ アラート] で安全な公式検証に対応したイベントを確認します。

> **Note** 要確認: 現行の plan / subplan / extension、無料枠、安全な検知試験は（初回で記入）です。有効化だけで検知成功とは扱いません。Agent 365 のエージェント単位機能は対象外です。

### Defender CSPM (任意)

1. 管理者が費用と対象範囲を承認した場合だけ CSPM を有効化します。
2. 変更前後の状態と対象範囲を記録します。

### 評価・レッドチーム

1. [合成プロンプト](../assets/prompts/README.md) で評価対象と期待結果を決めます。
2. GA の評価機能だけを使って実結果を記録します。
3. Japan East で GA の Red Teaming を利用できるか確認します。
4. 利用条件を確認できない機能は未実施として記録します。

> **Note** 要確認: 継続評価 UI・個別 evaluator・Red Teaming の提供・課金・上限はこの章で確認します。Preview 機能の操作は載せず、GA 後に追記します。新しい C 番号は追加しません。

## 9.4. 完了条件

Policy の検出・拒否確認（C06）の Audit による検出と Deny による拒否を、この章の別試験として記録します。脅威検知の確認（C07）は設定の存在と実際の検知イベントを区別します。評価・レッドチームの実施状況も別記します。

```bash
bash scripts/verify.sh --section 8
```
実行結果の確認ポイント: 旧セクション番号8を指定する設定収集用コマンドです。実操作の合格は返しません。

## 9.5. うまくいかない場合

（初回で記入）

1. 割当スコープと定義の effect を確認します。
2. Deny が BYO の復旧を妨げる場合は、当該リソース・期間・理由を限定した例外を管理者と確認します。
3. 例外の手続きが未確定なら復旧の変更を保留します。
4. 他リソースまで一括で Deny を解除しません。

## 9.6. 次の操作

試験結果を保存したら第10章へ進みます。Defender の復帰と環境削除はその章で行います。
