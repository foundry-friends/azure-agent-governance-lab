# 8. 権限・認証・ネットワークの統制を試す

進め方: README の第0〜10章を順番に実施します。第7章の完了条件を満たしてから進めます。

> **Note** 状態: 操作ドラフト（Learn 2026-09 時点の記述に基づく・Azure 未実行）。2026-09-20 改訂。第7章の初回実行の結果を記録するまでは、本章の動作試験を開始しません。

> **補足** この章では環境を削除しません。通常の削除は最後の第10章です。中断して片付ける場合だけ、第10章へ進みます。

## 8.1. 目的

同じ環境・エージェント・合成入力で、許可される操作と拒否される操作を比較します。対象は C02／C03／C08／C09 と、その証跡を確認する C04／C05 です。第4・7章の正常応答 C01 を比較の基準にします。

### なぜこの作業が必要か

設定値が正しくても、実際の呼び出しが意図どおり許可・拒否されるとは限りません。例えば、権限を別のスコープから継承しているユーザーでは、呼び出し専用ロールだけの効果を確認できません。

正常な呼び出しを基準にして、主体・認証・接続元の条件を一つずつ変えます。失敗時には拒否した層を特定し、通信障害やログイン失敗を RBAC・IP 制限の成功と取り違えないようにします。

### 作業前に知っておくこと：拒否されたら合格、とは限らない

| 確認すること | 比較で変える条件 | 確認したい拒否 |
|---|---|---|
| 認可（C02） | サインインするユーザーの権限 | 本人は認証できたが、Foundry の操作権限がない |
| 認証（C03） | 対象への認証情報の有無 | 対象サービスが認証情報のない要求を拒否 |
| ネットワーク（C08） | 接続元 | 同じ主体・操作でも、許可外の経路からは届かない |
| quota（C09） | 同じ集計期間内の要求数 | 認証できる主体でも、決めた回数を超えると拒否 |

例えば、無権限ユーザーがサインイン画面で止まっただけでは、Foundry の権限による拒否は確認できません。**期待した層で拒否された証拠があって Pass、許可されない操作が通れば Fail、比較条件や証拠が足りなければ Pending**として記録します。

第7章の必須条件が欠ける場合は構築工程で止めます。特に工程8〜10のツール仕様・登録手順が未確定の現状では、この文書を見直し済みでも本章の実機試験を開始できる状態とは扱いません。本文監査など、前章から明示的に保留した項目がある場合は、その行を保留したまま実施可能な試験を進めます。

### 実行場所と記録方法

- GUI は Azure portal／Foundry portal、データ面の正常応答は社内 PC のブラウザで確認します。
- 本章の Bash は Cloud Shell での設定照会・補助スクリプトだけです。第7章の社内 PC の CLI 例外は ZIP 配布とその認証・対象確認に限ります。
- 未認証・別のサービス主体による要求は、対象・HTTP メソッド・認証方式を固定できる承認済みの試験経路が用意できた場合だけ実施します。現時点ではその実装は未確定です。
- トークン・キー・Cookie を手動でコピーして証跡に残しません。試験のために IP 制限・認証・条件付きアクセスを解除しません。

各試験は「許可条件で成功 → 条件を一つ変えて拒否 → 許可条件で再び成功」の順で行います。基準の成功がない場合は、比較試験を Pass にしません。

同梱アプリは会話を引き継がず、1回の送信で1往復だけを要求します。[新しい会話] ボタンを探す必要はありません。画面を開き直して前回の応答を消し、1回ずつ送信します。期限切れ時の認証更新による1回の自動再送は別に記録し、タイムアウト時に手動で連打しません。

| 手元に揃える情報 | 確認元 |
|---|---|
| アプリの HTTPS URL・版、対象 project・エージェント | 第7章の配布後確認。Basic 分岐時は現在使用する対象 |
| User・Consumer・無権限ユーザーのサインイン名 | 第5章の主体と権限の記録。管理者とは別のブラウザプロファイルを用意 |
| 正常入力 | 合成プロンプト集の「正常応答」の1文。全ユーザーで同じ文章を使用 |
| 開始時刻・接続元・期待結果 | 試験前に非公開記録へ記入。時刻にはタイムゾーンを付ける |
| ログを確認する担当者 | LAW、App Service、Entra の閲覧権限を持つ担当者。試験ユーザーに監査権限を追加しない |

### アプリの表示とHTTP結果の読み分け

アプリ画面には相関 ID・失敗した層・メッセージが表示されます。HTTPコードや上流ステータスは画面には表示されないため、必要な場合は構築担当が対象 App Service の [Log stream] を開き、同じ相関 ID のログの `status` と `status_upstream` を照合します。トークンや要求ヘッダーをコピーする必要はありません。

| 表示・ログの例 | 記録するときの注意 |
|---|---|
| `foundry_authz`、アプリ `status=502`、`status_upstream=403` | Foundry から403が返った候補。ネットワーク拒否も照合し、ロール拒否と即断しない |
| `foundry_authn`、アプリ `status=502`、`status_upstream=401` | Foundry 側の認証拒否。アプリ入口の401とは別 |
| `entry`／ログイン画面／接続失敗 | 後段まで要求が届いたか確認する。これだけでFoundryの認可試験を合格にしない |

画面の層名は[同梱アプリ仕様](../assets/app/README.md)による分類です。相関 ID のログが見つからない場合は、コードを推測して記入せず、HTTP結果・拒否層を未確認として残します。

## 8.3. 権限と認証を試す

### C02：ユーザー別の権限を比較する

1. 第5章の割当記録を開き、対象 project と3種類のユーザーの ID を照合します。
2. 構築担当の Azure portal で対象 Foundry account を開き、[アクセス制御 (IAM)] → [アクセスの確認] を選択します。
3. 試験ユーザーのサインイン名で検索し、直接・グループ・継承の割当を確認します。project の割当は第5章5.3の工程2の照会で再確認します。
4. 管理者とは別のブラウザプロファイルを開き、今回のアプリ URL にアクセスします。
5. サインイン画面で Foundry User の試験ユーザーを選択します。別ユーザーが自動選択された場合は送信せず、試験用セッションを分け直します。
6. 表示されたエージェント名を第7章の記録と照合します。
7. 入力欄に合成プロンプト集の「正常応答」を貼り付けます。
8. [送信] を1回選択し、応答を待ちます。[会話メモを保存] は押しません。
9. 時刻・主体・応答の有無・相関 ID・失敗した層を非公開に記録します。
10. [サインアウト] を選択し、そのユーザーの試験用ウィンドウを閉じます。プライベートモードでは同じセッションの全ウィンドウを閉じます。
11. Consumer 用の別プロファイルで手順4〜10を繰り返します。
12. 無権限ユーザー用の別プロファイルで手順4〜10を繰り返します。
13. Foundry User のプロファイルで同じ入力を再送し、正常応答が回復することを記録します。

各ユーザーのサインイン完了と、Foundry の呼び出し結果は別の欄に記録します。前のユーザーの画面を残したままアカウント名だけ切り替えたと判断しません。

RG の割当画面だけでは子のプロジェクトへの割当を網羅できません。試験中に既存の管理者権限を外すのではなく、余分な権限のない検証用主体を使います。

| 主体 | 本人経路での呼び出し | エージェント作成・編集 | 判定上の注意 |
|---|---|---|---|
| Foundry User | 成功 | 成功 | モデルのデプロイや公開の権限とは分ける |
| Foundry Agent Consumer | 成功 | 拒否 | APIM のサービス主体の成功では代用しない |
| 無権限ユーザー | 拒否 | 拒否 | Easy Auth・条件付きアクセス・IP 制限で先に拒否された場合、Foundry RBAC は Pending |

作成・編集はアプリ画面ではなく [Microsoft Foundry](https://ai.azure.com) で試します。正常呼び出しの基準に使うエージェントは編集しません。

1. Foundry User のプロファイルで Microsoft Foundry を開き、今回の project を選択します。
2. [ビルド] → [エージェント] を開きます。
3. [エージェントの作成] を選択します。
4. 名前に `<試験用エージェント名>`、モデルに第4章の承認済み配置を指定します。名前は通常のエージェントと区別します。
5. 第4章の初回照合で確認した保存操作を行います。
6. エージェント一覧へ戻り、試験用の名前を選択して設定が保存されたことを確認します。
7. 指示欄の変更前の内容を非公開に控え、「短く答えてください」を追加します。
8. 保存後に一覧から開き直し、指示の反映を確認します。
9. 試験用エージェントの画面 URL・作成者・名前と、作成／編集それぞれの結果を記録します。
10. Consumer の別プロファイルで同じ project の [エージェント] を開き、作成と、手順9の試験用エージェントの編集を別々に試します。作成できてしまった場合は別名で記録し、Fail として以後の試験を止めます。
11. 無権限ユーザーでも、同じ対象への作成／編集の可否を別々に確認します。開けない画面の操作を、実行できたと記録しません。

> **Note** 要確認: 作成画面・保存方法は第4章の初回記録と照合します。保存済みか判断できない場合、作成・編集の結果を Pending にします。エージェントの公開や試験ユーザーへの権限追加で回避しません。

作成ボタンがない結果は「GUI 操作不可」と記録します。バックエンドへの作成・編集要求を送れなければ、その API 拒否は Pending です。編集は対象の所有関係も記録し、作成拒否とは別に判定します。試験用エージェントは第10章の片付け対象として記録します。

### C03：認証設定を照合する

構築担当の Azure portal の検索欄から、今回のリソースを1つずつ開きます。第3・4章で記録した名前と ARM ID を照合し、下表の画面で設定値を確認します。キーを表示・取得しません。

| 対象 | 設定画面への入り方 |
|---|---|
| Storage | [設定] → [構成] でストレージアカウントキーのアクセス許可を確認 |
| Search | [設定] → [キー] でロールベースのアクセス制御のみの設定を確認。キー値は開かない |
| Cosmos DB／Foundry | 第3・4章の設定記録を開き、下記の管理面照会で値を再確認 |

| 対象 | 期待する設定 |
|---|---|
| Storage | `allowSharedKeyAccess=false` |
| Cosmos DB・Search・Foundry account | `disableLocalAuth=true` |

Azure portal 上部の [Cloud Shell] → [Bash] を開き、第5章の対象確認を行います。下の `<target-resource-id>` を完全な ARM ID に置き換え、各リソースについて1回ずつ実行します。

```bash
az resource show --ids "<target-resource-id>" --query '{type:type,disableLocalAuth:properties.disableLocalAuth,allowSharedKeyAccess:properties.allowSharedKeyAccess}' --output json
```
実行結果の確認ポイント: リソース種別に対応する上表のプロパティが期待値であり、対象プロパティが null／欠落していないことを確認します。

上表に関係しないプロパティの null は判定対象外です。対象プロパティを取得できなければ、API の表示差か設定不足かを切り分けるまで Pending にします。

### C03：認証成功と未認証拒否を比較する

| 対象 | 許可条件 | 拒否条件 | 記録する結果 |
|---|---|---|---|
| アプリ入口 | 社内 IP・サインイン済み | 同じ社内 IP・未サインインの別プロファイル | 認証要求または拒否。Foundry の拒否とは別 |
| Foundry | 許可された本人・同じ API 操作 | 同じ送信経路・操作で認証情報なし | 対象 API の認証拒否と相関情報 |
| データ基盤 | 第4章の許可サービス主体の操作 | 同じ対象・操作で認証情報なし | サービスごとの認証拒否。経路未用意なら Pending |

**アプリ入口の未サインイン比較**は、次の順で行います。

1. 社内回線から、C02で成功したユーザーで正常入力を送り、時刻を記録します。
2. 認証済みの試験セッションとは別に、サインイン情報を持たないブラウザプロファイルを開きます。
3. 同じアプリ URL を開きます。ここでは資格情報を入力しません。
4. Easy Auth の設定どおりサインインを要求されることを記録します。自動サインインされた場合は未認証試験にならないため、Pending としてセッションの用意を見直します。
5. 未サインインの試験ウィンドウを閉じます。
6. 元の許可ユーザーのプロファイルで正常入力を送り、再び応答することを確認します。

**Foundry／データ基盤の未認証要求**は、承認済み試験経路が用意できた場合だけ、正常要求→同じ操作で認証情報なし→正常要求の順に比較します。現状では対象 API・HTTPメソッド・要求生成の操作手順が未確定なので、トークンを手動で抜き取ったりアプリを改造したりせず Pending として残します。

URL をブラウザで開いただけでは、認証拒否とメソッド違いを区別できません。アプリのログイン画面も Foundry の未認証拒否の証拠にはなりません。未認証要求を送れる経路がなければ、設定照合だけ完了として動作試験を Pending にします。本章で新たなキー取得・キー認証の拒否試験は行いません。第4章A13の承認済みの旧キー確認は別の工程であり、その結果・未確認事項を引き継ぎます。

### 設定照会用スクリプト (任意)

Cloud Shell にリポジトリと非公開の `.env` を用意した場合だけ使います。`AZURE_SUBSCRIPTION_ID`、`AZURE_TENANT_ID`、`AZURE_RESOURCE_GROUP`、`FOUNDRY_ACCOUNT_RESOURCE_ID` を今回の対象と照合します。

```bash
bash scripts/verify.sh --section 2
```
実行結果の確認ポイント: account スコープのロール・認証設定の収集と Pending 表示を確認し、終了コード 2 を動作試験やプロジェクト RBAC の合格と扱いません。

設定不足や照会失敗はエラーとして切り分けます。旧 CLI 番号 2 は本章番号ではありません。

## 8.4. ネットワーク・ツール・証跡を確認する

### C08：人の入口の IP 制限

1. 組織が認めた社外試験回線と切替方法を確認します。用意できない場合はこの行を Pending にします。
2. 社内回線でC02の成功ユーザーのプロファイルを開き、同じアプリ・正常入力で応答を確認します。
3. 時刻・相関 ID・接続元回線を記録します。
4. 組織の方法で接続元だけを社外試験回線に変更します。VPN・プロキシで引き続き社内出口を使っている場合は許可外 IP の比較にしません。
5. 同じプロファイルで同じアプリ URL を再読み込みします。前の応答が表示されたままの状態を到達成功と判断しません。
6. 画面が開ける場合は同じ正常入力を1回送信します。入口で拒否された場合は、表示されたエラーと時刻を記録します。
7. 構築担当が第7章の App Service の [ネットワーク] → [アクセス制限] で今回の許可規則を照合します。規則は変更しません。
8. 同時刻の証跡から、App Service の入口とEntraのどちらで拒否されたかを確認します。
9. 承認済みの社内回線へ戻します。
10. 同じアプリを再読み込みし、同じ主体・入力で正常応答を再確認します。

許可外 IP からの拒否が期待結果です。社外試験用の回線が用意できなければ Pending にします。Entra のサインインログに条件付きアクセスの拒否がある場合は、その事実を別に記録し、App Service の IP 制限を確認したとは扱いません。403 だけでは拒否した層を確定しません。

### C08：サービス間の経路

| 経路 | 操作と確認 | 判定の限界 |
|---|---|---|
| App Service → Foundry | 第7章の VNet 統合・サービス エンドポイント・Foundry 規則を照合し、同じプロジェクト API の正常応答と突き合わせる | 設定と許可経路の成功を記録。許可外送信元の拒否まで証明したとは扱わない |
| Foundry の許可外送信元 | 有効な本人認証・同一 API 操作を送れる承認済みの別経路がある場合だけ比較する | 試験経路がない場合は拒否試験を Pending。アプリの VNet を解除して試さない |
| Agent Service → Cosmos / Storage / Search | 第4章 C08 の対象別の到達結果を確認し、今回の正常応答と照合する（Basic の BYO 行は対象外理由を明記） | App Service の VNet 統合だけでこの経路を解決したとは扱わない |
| Agent Service → ツール用 APIM | 登録済みの架空在庫ツール入力を送り、APIM の対象 API・操作・時刻とバックエンド成功を照合する | ツール API はネットワーク上は公開し、Entra の許可主体で保護する。社内 IP のみの制限を期待しない |
| ツール API の拒否 | 同じ操作について未認証と許可外主体を分け、承認済み試験経路から比較する | tenant・audience・許可主体のどの検証で拒否したか記録。経路未確定なら Pending |
| 未許可ツール | [合成プロンプト集](../assets/prompts/README.md)の未許可先を試し、登録制限・認可・APIM のどこが拒否したか確認する | DNS 失敗やモデルの自主的拒否だけなら強制点の証明は Pending |

各行の実行前に、対象 URL／API・操作・許可主体・拒否条件・ログ参照先を非公開記録に揃えます。正常応答は第7章のアプリ操作、ツール入力は合成プロンプト集の該当行を使い、[送信] 後の時刻・相関 ID を記録します。未認証・許可外主体・許可外送信元の要求方法が未確定の行は操作せず Pending にします。

ツール API の ID による拒否と、アプリ入口の IP 制限は別判定です。未許可ツールの強制点が確認できても、送信ネットワーク全体の遮断を確認したとは扱いません。公開へ緩めた経路で成功した場合は例外として記録し、制限下の到達を Pass にしません。

補助 CLI の現状を確認する場合だけ使います。

```bash
bash scripts/verify.sh --section 3
```
実行結果の確認ポイント: 現行スクリプトは Pending の案内と終了コード 2 を返すだけで、ネットワーク設定の自動収集や動作試験を行いません。

### C09：ツールの経由ログと quota

チャット送信回数とツール API の呼び出し回数は一致しません。接続初期化・再試行・複数ツール呼び出しもあるため、正常入力を連投して上限試験の代わりにしません。

| 事前に固定するもの | 記録する値 |
|---|---|
| 対象 | 第7章で確定した検証用ツール API と操作 |
| 認証 | 正常応答済みの許可サービス主体 |
| ポリシー | `quota-by-key`、適用スコープ、変更前の設定 |
| 集計 | 検証済み主体から作るキー、上限 N、期間、期間内の既存カウント |
| 試験の上限 | N を小さく設定した場合の最大要求数、停止時刻、再試行なし |
| 復旧 | 元のポリシー値と復旧確認担当 |

> **Note** 要確認: 第7章のツール実体・認証・quota の具体値と、要求数を制御できる試験経路が未確定です。確定前は以下を実行せず Pending にします。通常の会話から MCP の要求数を正確に制御できるとは扱いません。

1. Azure portal の対象 APIM を開き、[APIs] → [APIs] → 第7章の検証用 API を選択します。
2. [Design] → [Inbound processing] の [</>] を開き、変更前のポリシーを非公開に記録します。
3. 確定済みの `quota-by-key` の上限・期間だけを試験値へ変更し、[Save] を選択します。[Calculate effective policy] で対象 API／操作に適用される値を再確認します。
4. 新しい集計期間であることと、別の試験が同じキーを使っていないことを確認します。
5. 決めた最大要求数の範囲内で、無害な同じツール操作を順番に実行します。
6. 上限内の成功と超過時の応答を、APIM ログ・適用ポリシーと照合します。
7. 同じ API／操作の [</>] を開き、変更した値だけを元へ戻して [Save] を選択します。再度有効なポリシーを表示し、変更前の記録と照合します。
8. カウンターの期間終了など、許可条件が回復してから正常応答を確認します。

`quota-by-key` の `renewal-period` は最小 300 秒です。上限到達前に期間が切り替わった場合や、予期しない追加呼び出しがあった場合は、その回を合格にせず原因を記録します。期待する超過応答は 403 ですが、認証・認可の 403 と区別します。429 は別のレート制限として記録します。想定した拒否が出なくても、決めた要求数を超えて呼び続けません。ポリシー値を戻しただけで既存カウンターがリセットされたとは扱いません。

サービス基盤の再起動時には、上限到達後も短時間要求が処理される可能性があると Learn に記載されています。想定外の成功はその時刻・要求数と合わせて切り分け、即時かつ厳密な課金停止の保証には使いません。

この試験はツール呼び出しの quota です。本人経路・内部モデル呼び出しのトークン量や総費用を制限した証明にはしません。

### C09：Foundry 側のガードレール

1. 第4章の承認モデルと適用済みのフィルター／ポリシーを照合します。
2. 正常入力で応答を確認します。
3. [合成プロンプト集](../assets/prompts/README.md)の「公開例に沿った拒否入力」から公式資料を開き、対象モデルの GA 機能に対応すると確認できた例を1つ選びます。対象機能と結果の取得方法が未確定なら、送信せず Pending にします。
4. 同じアプリの入力欄をその例に置き換え、[送信] を1回選択します。
5. 応答と、利用可能なフィルター結果・拒否メタデータを記録します。同梱アプリはフィルター詳細を画面に出さないため、画面の断り文だけでは判定しません。
6. 正常入力へ戻し、[送信] を選択して正常応答を再確認します。

モデルが文章で断っただけの結果と、サービス側フィルターの適用を区別します。対象の GA 機能や結果の取得方法が確定しなければ Pending です。classic 向け資料の画面操作を現行 Foundry にそのまま当てはめません。エージェント向け Preview 介入点は対象外とし、存在しない RAI ID による fail open の再現は本編では行いません。

```bash
bash scripts/verify.sh --section 7
```
実行結果の確認ポイント: 現行スクリプトは Pending の案内と終了コード 2 を返すだけで、quota 超過やガードレールを自動試験しません。

### C04／C05：証跡を突き合わせる

1. 監査担当の Azure portal で第6章の LAW を開きます。
2. [ログ] を選択し、[KQL モード] で今回の LAW スコープを確認します。
3. 第6章のクエリのテーブル名・対象 ARM ID を置き換え、試験時刻を含む範囲で [実行] を選択します。
4. 結果の対象行を展開し、時刻・操作・結果・主体を非公開の試験記録と照合します。
5. ツール経路は第7章のAPIMログのクエリを使い、`ApiId`・`OperationId`・`CorrelationId`・`ResponseCode`・`BackendResponseCode` を照合します。APIMスコープで照会し、アプリの相関IDと同一とは推測しません。
6. App Service の結果は「アプリの表示とHTTP結果の読み分け」の手順で確認します。
7. どこまで届いたか、どの層で拒否されたか、未到着のログがあるかを試験記録へ追記します。

**サインイン段階で拒否された場合**は、権限を持つ監査担当が次を確認します。

1. [Microsoft Entra 管理センター](https://entra.microsoft.com) を開き、対象テナントを確認します。
2. [Entra ID] → [監視とヘルス] → [サインイン ログ] を開きます。
3. 試験時刻・ユーザー・対象アプリに対応するサインインを選択します。
4. 詳細の状態・失敗理由を確認します。
5. [条件付きアクセス] タブで適用結果を確認します。既存ポリシーは変更しません。
6. 結果と確認時刻を非公開に記録します。

ログと条件付きアクセスポリシーの両方を閲覧できる必要があります。表示できない場合は既存の担当者へ照会し、「適用なし」と判断しません。試験ユーザーに管理権限を追加する手順ではありません。

入口で拒否された要求に、後段 Foundry／APIM のログがないこと自体は異常ではありません。APIM の成功ログも、本人の Foundry 呼び出しを記録したものではありません。ログの未到着・対象違い・拒否を区別します。

C04 の診断イベント到着と、C05 の本文トレース・閲覧制御は分けます。第6章で保留した C05 は本章でも保留し、本文を取得できない結果を本文監査の成功にしません。認証情報や不要なプロンプト本文を採取しません。

## 8.5. うまくいかない場合

| 順序 | 操作 |
|---|---|
| 切り分け | 主体・継承権限・送信元・対象 API・操作・時刻を照合し、入口／認証／Foundry RBAC／ツール／バックエンドのどこで止まったか確認する |
| 代替 | GUI で不足する設定は既存の Cloud Shell 照会で確認する。動作要求を送れない場合は、その行を Pending とする |
| 記録 | 期待と実際、拒否した層、証跡、未確定事項、必要な試験経路を非公開の `evidence/` に残す |
| 元に戻す | quota の試験値を変更前に戻し、社内回線・許可主体・正常入力で再確認する。復旧できなければ次の試験を止める |

IP 制限や Entra 条件付きアクセスを緩めて試験を続けません。BYO 到達の問題は第4章の切り分け記録と照合します。期待する拒否が実際には通った場合は Fail、試験経路や根拠が足りず評価できない場合は Pending とします。

## 8.6. 完了条件と次の操作

1. 非公開の試験記録を開き、各 C 番号の試験行ごとに下表を記入します。
2. 許可時・拒否時・復旧後の3つの結果を対応付けます。Consumerの呼び出しなど成功同士の比較は、その期待結果を明記します。
3. Pending の行に未実施理由・必要な条件・担当を記入します。
4. 保存後に記録を開き直し、空欄を合格扱いしていないことと、設定の復旧結果を確認します。
5. 手順の不足・差分は第0章の Excel に記録し、修正が必要なものを Issue に転記します。実 ID・本文・生ログは非公開記録だけに置きます。

| 記録項目 | 内容 |
|---|---|
| 識別 | 実施日・時刻とタイムゾーン、Run、章・手順、C 番号、試験行 |
| 条件 | 対象の別名、主体の役割、アプリ・モデル・エージェントの版、合成入力の識別名、変更した条件 |
| 結果 | 期待、実結果、HTTP 結果、拒否した層、Pass／Fail／Pending |
| 証跡 | 非公開ログの参照先と相関情報。秘密値は含めない |
| 続き | 未実施理由、解決する条件、担当、設定復旧と正常再確認の結果 |

[確認項目](../checks/README.md)と照合し、未実施行を残した C 番号を全体 Pass にしません。C01 の正常応答を再確認し、実施可能な試験・保留理由・復旧結果が揃ったら第9章へ進みます。認可されない操作の成功など、環境の保護に関わる Fail や復旧失敗が残る場合は、修正と再試験まで進みません。第6章からの C05 など明示した保留は引き継ぎます。「第8章の記録完了」と「全項目の合格」は区別します。
