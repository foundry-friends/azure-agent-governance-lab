# A. 作り込み（hosted agent）の分岐 (任意)

本編の第0〜10章とは別の参考資料です。本編の続きとして環境を再作成する手順ではありません。

> **Note** 状態: ドラフト（Learn 2026-09 時点の記述に基づく・未実行）。更新日 2026-09-17。採用判断と検証設計を扱います。実装・配布物・Azure での動作確認は未完了です。

## A.1. 目的

prompt agent で表現しきれない処理をコードで実装する場合に、hosted agent を選ぶ条件と追加の責任を確認します。[D11](90-design-decisions.md#d11-の適用範囲) の本編を prompt agent とする判断は維持します。

### なぜこの作業が必要か

コードで処理を組めるようになると、分岐や外部連携を細かく設計できます。一方、依存パッケージ、イメージ、実行中の状態、権限、障害時の再実行も管理対象になります。ホスティングをサービスへ任せても、アプリの認可やツール実行の妥当性まで自動で保証されるわけではありません。

この付録では、追加する理由を先に決め、提供状態と本編の制約に合うかを確認します。hosted agent の採用を、第4章の未解決条件の回避策とは扱いません。

## A.2. 前提と提供状態

2026-09-17 に取得した公式資料では、Microsoft Foundry Hosted Agents のサービスは GA です。一方、Agent Framework の Python ホスティング連携はプレリリースと明記されています。サービス、SDK、個々の機能の提供状態を分けます。[公式のホスティング説明](https://learn.microsoft.com/ja-jp/agent-framework/hosting/foundry-hosted-agent)を参照します。

| 対象 | この付録での扱い |
|---|---|
| Hosted Agents サービス | GA の説明を確認済み。ただし、このラボのリージョン・権限・ネットワークでの成立は未検証 |
| Python ホスティング連携 | プレリリースの導入例は本手順へ採用しない |
| 送信先制御（network egress controls） | Preview のため設定・試験手順は対象外 |
| Managed VNet | Preview の作成コマンドを使う手順は対象外 |
| RAI ポリシー | 参照先の存在と実際の効果を別々に確認する。現行サンプルに含まれる Preview 指定をそのまま実行しない |
| 閉域・private ACR | 本編では構築しない。本番側の別設計として適用条件を調べる |

旧 Preview の起動・停止・レプリカ管理を、現行の実行モデルに混ぜません。現行版はセッションの利用に応じて compute を管理します。旧 Preview backend からは自動移行されないことも公式の移行資料に記載されています。新規検証では過去のサンプルをそのまま起点にしません。

> **Note** 要確認: 安定版の SDK／プロトコルライブラリ／管理 API の組合せ、Japan East の利用可否、公開 endpoint の制限、イメージ取得経路が本編の条件を満たすことを、実装前に確定します。GA のサービスという理由だけで構築を開始しません。

## A.3. 採用判断と実装前の準備

### prompt agent と使い分ける

| 必要なこと | 判断の起点 |
|---|---|
| プロンプトと許可したツールで応答を組み立てる | 本編の prompt agent を維持する |
| 独自コードで複数段の処理や状態遷移を制御する | hosted agent を候補にする |
| 独自の要求形式や処理ライブラリを使う | プロトコルと安定版ライブラリの適合性を確認する |
| 本人ごとの権限でデータへアクセスする | 呼び出し元のユーザーと agent identity の権限を別々に設計する |
| 任意の外部送信を防ぐ | GA の強制手段を確定する。APIM の許可先設定だけでコードからの直接送信まで防げるとは扱わない |

hosted agent は独自コードをコンテナー化して配置する方式です。第7章の呼び出し用 App Service は UI と本人認証の入口であり、hosted agent の実行環境へ自動で変わるものではありません。

### 作成する前に決める

1. prompt agent では不足する処理を一つ記録します。
2. その処理に必要な入力・出力・保持する状態を記録します。
3. 使用するプロトコルと依存関係の固定版を決めます。
4. コンテナーイメージとレジストリの所有者を決めます。
5. 呼び出し元と agent identity の権限を表にします。
6. モデル・ツール・データへの通信経路を表にします。
7. 失敗時の中断・再試行・重複実行防止を決めます。
8. 追加費用と削除対象を台帳に記録します。

| 設計項目 | 記録する値 |
|---|---|
| 実装 | 処理の目的、ソースの版、依存パッケージの固定版、イメージの digest |
| 状態 | ユーザー・会話・セッションの識別方法、保持期限、削除方法 |
| ID | 呼び出し元、agent identity、各下流サービスの対象スコープとロール |
| 通信 | 発信元、宛先、認証、許可条件、拒否を強制する場所 |
| ツール | 許可した処理、引数検証、実行前承認が必要な操作、再実行時の扱い |
| 運用 | 正常性確認、タイムアウト、ログ、担当者、版の切替と復旧方法 |

[D14](90-design-decisions.md) の App Service VNet 統合は App Service の送信経路です。hosted agent の送信経路として流用したとは扱いません。APIM Basic v2 は引き続きツール経路の候補であり、本人経路の代理認可を自動で担いません。

> **Note** 要確認: このラボの「閉域なし・全公開なし・送信先を限定・キー認証なし」を同時に満たす hosted agent の構成は未確定です。承認操作や Purview 連携も候補段階です。採用条件がそろうまではコード・配布コマンド・Azure 作成手順を追加しません。

## A.4. 検証の設計

将来、構成と実装を確定した場合は次の行を別 Run の証跡に記録します。いずれも現時点は Pending です。C01〜C10 の番号は増やさず、該当する C 番号の追加試験として区別します。

| 対応 | 試験 | 期待する証拠 |
|---|---|---|
| C01 | 合成入力に対する一往復 | 狙った agent の版・モデル・データを使った応答 |
| C02 / C03 | 許可主体・無権限主体・未認証の比較 | 成功／拒否したサービスと認証方式を特定できる |
| C04 / C05 | 操作ログ・本文・閲覧権限 | 操作ログと本文を区別し、本文は許可者だけが参照できる。未対応なら Pending |
| C08 | 許可したツールと許可外の送信 | APIM 経由の成功と、迂回を含む許可外通信の拒否を別々に確認できる |
| C09 | RAI の参照と効果 | 存在するポリシーを参照し、合成の正常入力と拒否対象を比較できる |
| C10 | agent・状態・関連資産の廃止 | compute、レジストリ、権限、保持データ、費用の残存を説明できる |

### RAI の設定済みと実際の防御を分ける

公式資料は、存在しない RAI ポリシー ID を参照していても agent が作成され、`active` になる一方で、フィルターが適用されない場合があると説明しています。作成成功だけで C09 を Pass にしません。[hosted agent のガードレール](https://learn.microsoft.com/ja-jp/azure/foundry/agents/how-to/add-hosted-agent-guardrails)を参照します。

1. 対象 account に RAI ポリシーが存在することを確認します。
2. agent の版が参照する完全な ARM ID と照合します。
3. 合成入力で正常応答と拒否の結果を比較します。
4. 結果を agent の版・ポリシー・日時とともに記録します。

この確認は将来の試験設計です。存在しない ID を使う fail open の意図的な再現は、現在の手順には含めません。本編の prompt agent で hosted 固有の現象を実証したとも扱いません。

## A.5. うまくいかない場合

| 症状 | 切り分け・次の判断 |
|---|---|
| ローカルでは動くが hosted で動かない | プロトコル、依存関係、実行 ID、状態の保存先を比較する。ローカルでのユーザー情報をクラウドにもあると仮定しない |
| イメージを取得できない | レジストリへの権限と通信経路を分けて調べる。解消のためだけに公開設定を緩めない |
| 自分の権限と違うデータが見える | 下流への呼び出しが本人委任か agent identity かを確認する。共用 identity で成功しても本人 RBAC の合格にはしない |
| RAI を付けたのに拒否しない | ポリシーの実在、版の参照、試験入力、拒否を担当する層を確認する |
| 古い管理コマンドが動かない | 現行の移行資料と使用 API を照合する。旧 Preview backend のライフサイクルを復元しない |

対象の版・期待結果・実結果・戻し先を記録します。機能制約が残る場合は検証を止めます。復旧時は既知の版へ戻したうえで、認証と許可先を再確認する設計とします。

## A.6. 終了と後片付け

この付録では資産を作成していません。採用判断の完了条件は、追加する理由、未解決条件、担当者、次の判断を記録できることです。hosted agent の動作成功とは区別します。

将来作成する場合は、作成前に [第10章](10-cleanup-cost.md) の削除台帳へ agent の各版、セッションの保持、コンテナーイメージ、レジストリ、agent identity の権限を追加します。自動で compute が解放されることと、保持データ・資産・費用の後片付けは別です。

> **Note** 要確認: 現行 API の agent／版／セッションの削除と、保持データの消去範囲を構築前に確定します。共有レジストリや共有 project を agent の後片付けのために丸ごと削除しません。

## A.7. 費用

[第10章の Excel v3 明細](10-cleanup-cost.md#107-費用) は prompt agent 主線の見積りです。No.1 の月額 $0.000000 に hosted compute が含まれるとは扱いません。No.14・15 のモデル利用や No.6 のログも、hosted に変更した場合は使用量を見直します。

公式資料では hosted runtime はアクティブなセッション中の CPU とメモリの利用に基づく課金です。追加見積りには実行時間と同時セッション数のほか、レジストリ、状態の保存、モデル、ツール、ログ、通信を含めます。単価は採用時の料金表で取得し、今回の No.1〜19 や既定月額へ無断で加算しません。

## A.8. 本番との差

本番では独自コードと依存関係の更新、イメージの検査、版の切替、権限の棚卸し、障害時の復旧を担当する必要があります。ネットワークやデータ基盤の差は [付録B](92-appendix-production-diff.md) を参照します。閉域構成や追加の統制をこの付録から展開しません。
